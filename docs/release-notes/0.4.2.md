# ANAS 0.4.2

ANAS 0.4.2 is a point release for the Datasets view, snapshot schedules
and the task grids. The pool-space chart grew past the page on a pool that
also holds Proxmox guest volumes, a recursive snapshot schedule had no way
to leave a child dataset out, retention never reached the children of a
recursive schedule, and a reboot made every task read as never run.

One thing does change on upgrade, and it is deliberate: the first run of
each recursive snapshot schedule applies its retention policy to the child
datasets it snapshots, which the previous releases never did. See the
retention section below before upgrading if you keep recursive schedules.

## The pool-space chart keeps its height

The Datasets view opens with a chart of how the pool's used space breaks
down across its top-level datasets. On a pool that is also Proxmox
storage, every guest disk image is a top-level dataset, and the chart's
legend listed each one. With enough guests the chart filled the page and
the dataset tree beneath it had no room left, with nothing to scroll.

Everything Proxmox owns on the pool, guest volumes and any registered
storage, is now one segment labelled Proxmox storage, the way the Name
column already sets it apart. The legend shows at
most six rows by name, the Proxmox storage row among them when there is
one, and folds the rest into one row whose tooltip lists them. The chart's height is fixed whatever the pool holds,
and the tree keeps the rest of the page.

## A recursive schedule can leave datasets out

A snapshot schedule with Include child datasets ticked snapshots the whole
tree under its target. An hourly schedule on a pool therefore took hourly
snapshots of every dataset under it, including the media library or the
backup target that only needs a daily one, and the alternative was one
schedule per dataset.

The schedule dialog now offers Exclude datasets once Include child
datasets is ticked, listing the target's children. An excluded dataset
and everything under it are left out of every run. The remaining
snapshots are still taken in one ZFS call, so they are as consistent with
each other as a plain recursive snapshot. A Proxmox storage root under
the target can be excluded the same way, which lets a pool carrying both
ANAS datasets and guest storage have one recursive schedule; the refusal
that used to stop such a schedule now names the dataset to exclude.
Snapshots this schedule already took on a dataset you exclude are removed
on its next run, and the dialog says so. Existing schedules are untouched.

## Retention now reaches every dataset a recursive schedule snapshots

A schedule with Include child datasets ticked took snapshots across the
whole tree under its target, but its retention policy was applied to the
target alone. Every child dataset kept every snapshot the schedule had ever
taken, and the space they held only grew.

Retention is now applied to each dataset the schedule covers, one snapshot
at a time. A held snapshot is never destroyed and does not use up a retention slot,
and it is reported only when the policy would otherwise have removed it. A snapshot that cannot
be destroyed because a clone depends on it is noted for that dataset and
the run carries on.

The first run after upgrading brings every child down to the policy. On a
schedule that has run for months that first run removes every child
snapshot beyond the retention count, which can be thousands, and it can
take a long time; the schedule's timer waits for it. If you want any of
those snapshots kept, hold them with `zfs hold` or raise the retention
count before upgrading.

A child that has an enabled schedule of its own with the same cadence is
pruned to the more generous of the two counts when the recursive schedule
runs. The child's own schedule still applies its own policy on its own
runs, as before. Snapshots the recursive schedule left on a dataset you
have since excluded are removed as well, unless an enabled schedule with
the same cadence covers that dataset. Only snapshots the schedule provably
took are removed from an excluded dataset; a snapshot that arrived there
by replication is left alone. A replica you keep under a recursive
schedule's target should be excluded from it, since the recursive
snapshot itself lands on the replica. If the schedule list cannot be read
during a run, that run prunes the target only.

The run's log and its notification list what was pruned per dataset.

## A reboot no longer resets a task's last run to "never"

After the node rebooted, every backup task, cloud sync task, replication
task and snapshot schedule read as never run until its next fire, although the next-run time
was right. The last run and its verdict were read from the service unit,
and systemd keeps those only until the next boot.

The grids now take the last run from the run's own record in the journal
when the service has nothing to say, so a task that ran last night still
says so after a reboot, with its result. If the journal no longer holds
that run, the row shows when the timer last fired and says plainly that
the result was not retained.

## Install

```
tar xzf anas-0.4.2.tar.gz && cd anas-0.4.2 && ./install.sh
```

Re-run over an existing install to upgrade. Hard-reload the browser
afterwards.
