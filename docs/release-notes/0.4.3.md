# ANAS 0.4.3

## New SMB shares give their users access to the folder

Creating an SMB share wrote the share to Samba and left the folder's
permissions as they were. A fresh pool's top folder belongs to root with
mode 755, so a share on it could be read but not written by the users it
named, and a guest share could not be written at all.

The SMB share dialog now has a box, ticked by default, labelled Grant the
selected users access on the share path. When the share is saved, each
user and group in Valid users gets Read-Write on the folder (Read on a
read-only share), and a share with guest access gives Everyone the same
level. The owner and owning group are left alone, existing grants are
kept, and nobody's existing access is lowered. New files and folders
inherit the grant.

Files already in the folder keep their permissions unless Apply to
existing files is ticked under the grant; that choice asks for
confirmation before anything is changed. Editing a share grants again
when its users, guest access, read-only setting or path change. Removing a
user from a share or deleting the share does not take any access away;
use Permissions on the share for that.

If the folder belongs to Proxmox storage, or the grant cannot be applied
for another reason, the share is still saved and a message says why the
grant did not run.

Both SMB shares and NFS exports have a Permissions button in the Shares
view. It opens the same Permissions dialog as the Datasets view, on the
share's folder. NFS exports have no user list, so this button is how their
folder is opened up.

## Permissions for Hybrid RAID pools

The Hybrid RAID view has a Permissions button. It opens the same dialog as
the Datasets view on the pool's folder: owner, owning group and everyone,
named users and groups, and Apply to existing files too.

Two things differ from a ZFS dataset, and the dialog says so where they
apply. A Hybrid RAID pool supports named users and groups without any
setting being switched on, so the note about enabling POSIX ACLs on the
dataset does not appear. Applying to existing files covers every subvolume
under the pool's data in one pass and never touches the pool's snapshots.

The button is unavailable while the pool is not mounted, or while an iSCSI
LUN's image file lives on the pool.

In every Permissions dialog, Apply to existing files too now asks for
confirmation before anything is changed.
## The disk health badge follows the array

The Disks view and the dashboard's disk-health counts judge every disk's
health badge from its SMART result and, when the disk is a ZFS pool member,
from the pool's word about it. A disk in a Hybrid RAID (AHR) pool was judged
by SMART alone. When the array marked a member failed, the pool's own view
flagged the failed member while the Disks view still showed the disk as
healthy and the dashboard counted it as such.

An AHR member now carries the array's word into the same badge: a member the
array has marked failed or missing reads critical, a member being rebuilt
onto a spare reads a warning, and a disk that slices several bands reads its
worst band. A disk whose SMART self-test failed stays critical whatever the
array says, and a disk the array is happy with keeps reading by SMART alone.

## A failed re-apply after a Proxmox upgrade is reported

A pve-manager or libpve-http-server-perl upgrade replaces the Proxmox files
that carry the ANAS section of the web UI, and ANAS puts its additions back
after every package installation or upgrade. When that step failed, nothing
recorded it, and the first sign was the ANAS section missing from the UI.

Every run is now logged to the system journal with its output and its
result, under `journalctl -t anas-pve-integration`. A failed run also sends
a Proxmox notification at warning severity, type `anas-integration`, through
your notification targets. It gives the cause and the command that puts the
integration back, run as root on that node:

```
/opt/anas/packages/pve-integration/install.sh
```

A failed re-apply never fails the apt run, and Proxmox itself keeps working.

## The installer names an incomplete release directory

When `install.sh` runs from a directory that holds only part of the release,
it stops before changing anything and now says which directory it checked,
every file missing from it, what a release unpacks to, and the fix: extract
the release archive into a fresh, empty directory and run `./install.sh`
from inside the directory it creates. A missing `VERSION` file is now one of
the reasons it stops.

## Install

```
tar xzf anas-0.4.3.tar.gz && cd anas-0.4.3 && ./install.sh
```

Re-run over an existing install to upgrade. Hard-reload the browser
afterwards.
