A cleanup release paid for by a real crash: a node lockup mid-build left an
AHR pool in every awkward state at once, and each fix here closes something
that weekend exposed. Destroy leaves nothing behind, create is immune to what
earlier versions left behind, a dead pool says so, sync advisories claim only
what md actually knows, and the installer plays fair with sibling projects.

## Destroy reaches every member, and create forgives what it couldn't (#16, #17)

Destroying a pool while a member disk was detached from its arrays (the most
likely state for a disk in a pool being destroyed after trouble) wiped only
the attached members — the detached disk kept its partitions, partlabels, and
live md superblocks, which mdadm's incremental assembly would happily
resurrect as ghost half-arrays at the next boot. Destroy now sweeps for
member partitions by partlabel across all disks, zeroes superblocks on
anything membership didn't cover, and names — never silently skips — a member
it cannot reach.

Separately: the LVM PV label lives ~128 MiB inside each band array's data
area, deeper than any partition-level wipe. When band arrays were dead at
destroy time (missing PVs), those labels survived on the platters, and an
identical-geometry recreate resurrected the old VG — `pvcreate` then refused
the "new" device without `-ff` and the create failed. Create now runs
`wipefs -a` on every freshly created md device before `pvcreate`:
a device ANAS just created can only contain stale residue, so create is
immune to this entire class regardless of what destroy could reach.

## A pool whose volume cannot assemble reads OFFLINE, not degraded (#18)

After the lockup, one band array was running degraded and two could not start
at all — the volume was unmountable and the data unreachable. The dashboard
said "degraded", which reads as reduced-redundancy-but-functioning. Total
unavailability now has its own pool state: `offline`, outranked only by
`failed`, derived when any band array cannot start or the logical volume is
inactive. Red pill on both surfaces, and the advisory names what's actually
wrong: which arrays cannot start, and that the data is unavailable.

Skew note: a browser still holding a cached 0.2.4 `anas.js` won't know the
new state's pill — the version-skew banner covers the window; hard-refresh
resolves it.

## Sync advisories state the observation, not a guess (#15)

md cannot distinguish a fresh array build from a rebuild onto a spare after a
disk is physically pulled — the superblock records no "has ever been
optimal", and the two shapes are identical in mdstat. 0.2.4 guessed anyway:
"building redundancy — no action needed", which is confidently wrong in the
pulled-disk case. Advisories now say exactly what md knows: "syncing onto
<disk> — no fault recorded" (the target named only when unambiguous), and
"sync queued behind another band — no fault recorded" for serialized bands.
The moment-of-failure notification remains the discriminating signal when a
disk actually drops. This closes 0.2.4's known issue by honesty rather than
divination; shadow-state markers were considered and rejected — a stale
marker would mislabel a real disk pull, the one direction a storage product
must not fail.

## The pveproxy hook uninstalls politely next to siblings (#20)

Uninstall restored a whole-file backup of pveproxy's `AnyEvent.pm` — which,
if another project had spliced its own hook after ANAS installed, silently
deleted the sibling's hook. When a foreign hook block is present, uninstall
now excises only ANAS's own marker block, and the result must pass `perl -c`
*before* it replaces the live file (a failed excision leaves the system
untouched — a dead `/anas` path is cheaper than a dead PVE UI). Install
likewise declines to take a "pristine" backup that would capture a sibling's
block.

## The port-conflict probe can't lie under pipefail (#21)

`ss | grep -q` in the installer: grep exits at first match, `ss` takes a
SIGPIPE, and under `set -o pipefail` the pipeline reports failure — so a
*listening* port could read as free, intermittently, at install time. The
probe now captures the listing and matches it directly; deterministic exit
codes, no race.

## Known issues

- On an `offline` pool, the individual band pills can still read amber
  "degraded" — the pool-level badge and advisory carry the truth. Band-level
  wording is a candidate follow-up.

## Install / upgrade

Untar on the PVE node and run `sudo ./install.sh` (re-running over an existing
install is the upgrade path; it will add samba/nfs-kernel-server if missing).
