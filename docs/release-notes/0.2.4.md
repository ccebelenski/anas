A field-bug release: mixed-sector AHR pools actually create, a building pool
looks like one, a failed create cleans up after itself, and Samba is installed
for you.

## Mixed 4Kn/512e AHR pools create and expand (#7, #8)

Creating an AHR pool that mixes 4Kn drives (4096-byte logical sectors) with
512e drives failed at the LVM step — `Devices have inconsistent logical block
sizes` — after the disks were already wiped and the arrays already building.
Mixed geometry is AHR's core use case, so this was the headline break.

The LVM stack is now built with `allow_mixed_block_sizes` (per-command — ANAS
never edits PVE's `/etc/lvm/lvm.conf`), btrfs is created with an explicit 4 KiB
sector size, and the same treatment covers expansion (`vgextend` with a
new-geometry band, stage-proven live under a mounted filesystem). The layout
preview and confirm gate now label a mixed-geometry selection before anything
is touched, and mixed layouts are refused up front on kernels older than 6.19
(md's configurable-LBS floor — checked against the running kernel, not the PVE
version).

## A building pool reads as building, not failed (#7, #9, #14)

A new multi-band pool builds its bands sequentially; the kernel serializes the
syncs, so queued bands sit degraded-shaped with no progress line. That
previously surfaced as pool state FAILED, "replace the failed disk" advisories
on brand-new arrays, and a DegradedArray notification per band at creation.

- New pool state `building`: every band syncing or queued, no faulty member.
- Queued bands read "building redundancy (queued behind another band) — no
  action needed"; a real fault still reads degraded with the replace-disk
  advisory.
- The md event hook recognizes the initial-build shape and logs it instead of
  notifying; a genuinely degraded start (missing or faulty member) still
  notifies exactly as before.
- Band pills on the dashboard and Details are neutral "building" during a
  no-fault build; a rebuild after a failure stays amber "rebuilding".

## A failed create rolls itself back (#11)

`ahr.create` wipes its disks first, so any later failure leaves only what the
job itself built. A mid-create failure now tears that back down automatically
(arrays stopped, superblocks zeroed, disks zapped, `mdadm.conf` unpinned), the
job reports the original error annotated that the disks are blank and create
can be retried, and the failure is surfaced through a PVE notification and a
dashboard card — never a silent half-built stack. A failed create whose
wreckage still exists (e.g. daemon restarted mid-rollback) shows the real
error with "Destroy and retry" guidance instead of bare vg/lv-not-found noise.

## Expansion hardening (#12, #13)

Two pre-existing expansion bugs found while stage-proving the mixed-sector fix:

- Opening a new top band writes a new partition to an in-service disk, and the
  kernel refuses to re-read a held disk's partition table — the slice never
  appeared and the job died minutes later mid-reshape. The partition step now
  publishes new slices with `partx` and verifies the device exists before
  reporting success.
- Resuming an expansion halted after its reshapes finished planned no
  `pv-resize` for the grown bands, stranding the capacity and making Resume a
  permanent no-op (the delivered-capacity invariant from 0.2.2 correctly
  refused to lie about it). Resume now derives pv-resize from system truth —
  any PV materially smaller than its device gets one — with a structural 1 GiB
  margin so LVM's inherent few-MiB metadata offset is never mistaken for
  stranded capacity.

## Samba and NFS are installed for you (#6, #10)

A fresh install did not include Samba, so adding a share user failed with a
raw `spawn smbpasswd ENOENT` — and on a Samba-less node the Share Users screen
failed to load at all. `samba` and `nfs-kernel-server` are now unconditional
installer dependencies alongside `mdadm`/`btrfs-progs` (re-running the
installer over an existing node adds them; `--install-deps` gates Node.js
only, and the docs now say so accurately). The daemon also degrades gracefully
without them: the Share Users list loads, user creation preflights `smbpasswd`
and refuses with an actionable message *before* creating the Unix account, and
the UI refreshes its grids after failed jobs instead of leaving ghost entries.

## Band anatomy in the UI

- Details: each band array row expands to list its member partitions — full
  by-ids with per-member sync state.
- Dashboard: member tiles show the band slice alongside the disk size
  ("slice 5.46 TiB · disk 20.01 TiB"), and band headers carry height, a state
  pill, and a live sync strip — including "queued behind another band" while
  the kernel serializes a multi-band build.

## Dev builds identify themselves

Iteration builds (`make-release.sh --dev`) stamp the commit into the version
(`0.2.3+dev.6a8a981`) in the tarball name, `/opt/anas/VERSION`, and the API,
so a fleet running dev code is distinguishable from the release it was cut
between.

## Known issues

- A rebuild onto a hot spare after a disk is physically *pulled* (rather than
  failing in place) is indistinguishable from a fresh build in md's reporting,
  and reads as "building" (#15). The moment-of-failure notification still
  fires; only the ongoing state label is affected.

## Install / upgrade

Untar on the PVE node and run `sudo ./install.sh` (re-running over an existing
install is the upgrade path; it will add samba/nfs-kernel-server if missing).
