ANAS 0.3.5 is a point release for pools that carry log, cache, spare,
special or dedup vdevs. There is nothing to do after upgrading: the vdevs
were always there, and the view is fixed.

## Log, special and dedup vdevs show in the pool view

On current ZFS, `zpool status` reports log, cache, spare, special and
dedup devices in their own sections. ANAS read only the cache and spare sections,
so a pool's log, special and dedup vdevs never appeared in the pool
detail, whether added from ANAS or from the command line. They now
appear under their own headings, mirrored or single, whole-disk or
partition-backed. (GitHub #66)

The same blind spot reached every screen that looked at the pool's
topology, and each is fixed:

- **Disks tab.** A disk whose only role is in a special, log or dedup
  vdev now carries its pool, vdev, role, state and error counts. A
  failing member of a special vdev raises a disk warning instead of only
  the pool-level degraded card.
- **Dashboard.** Pools with log or cache devices no longer produce
  phantom pools in the telemetry, and a special or log vdev's throughput
  is attributed to its own role rather than to data.
- **Replace disk.** The replace dialog lists the members of every vdev
  class, so a failed special-vdev disk can be replaced from the UI.
- **Pool composer (expand).** The advisor sees an existing special vdev
  and no longer suggests adding one; its warning about what a special
  vdev's loss means is shown.

## Remove a cache, log or spare vdev

The Pools toolbar gains **Remove vdev…**, listing the selected pool's
cache, log and spare vdevs. Removal is a plain job: ZFS drops these
instantly, nothing is destroyed. Data, special and dedup vdevs are not
offered; their removal is device evacuation, which ANAS does not do.
(GitHub #66)

## Replacing a partition-backed disk

The replace dialog named a partition-backed vdev member by its whole
disk, so on an SSD split between a log and a cache the slots were
indistinguishable and the replacement was refused by ZFS. Members are now
named by their partition, and a replacement or removal that could match
more than one device is refused with the candidates listed rather than
guessed.

Adding a vdev to a pool that a PVE storage uses is now refused the same
way removing one is; PVE owns that pool's topology.

## Clean Up Disks on a pool created from device names

Destroying a pool created on the command line from `/dev/sdX` names left
its ZFS labels in place, because `zpool status` reports no by-id path
for such leaves and the cleanup addressed devices by by-id only. Cleanup
now uses the leaf's real device path, so every member of every vdev
class is label-cleared and the disk reads as available afterwards.

## Notes

- Partition-backed vdevs are displayed, never managed: ANAS builds pools
  from whole disks. A partition added from the command line by its kernel
  name (`sdb2`) shows under that name and does not cross-reference to the
  Disks list; one added by its by-id path does.
- Disks on `mmcblk` devices resolve to their whole disk correctly in the
  Disks tab.

## Install

```
tar xzf anas-0.3.5.tar.gz && cd anas-0.3.5 && ./install.sh
```

Re-run over an existing install to upgrade. Hard-reload the browser
afterwards.

## Known issues

- Telemetry shows a partition-backed vdev member added by its kernel name
  under that name; it does not link to the Disks list. Members added by
  their by-id path do.
