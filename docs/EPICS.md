# ANAS — Epics & Stories

> **This is the live plan.** It holds what is being built, the rulings every
> change must respect, the serious candidates, and the things already rejected
> (so they are not re-derived). The full build history — every shipped story's
> design notes, live-proof accounts and incident write-ups — is frozen in
> **`docs/EPICS-HISTORY.md`**; read it only when you need the *rationale* behind a
> ruling. Rebuilt 2026-08-25 at the 0.2.12 → 0.3.0 boundary.

**Rules of this file**
- Only implement work that traces to a story here (CLAUDE.md). Not in a story ⇒ not in scope.
- Every story carries a status tag: `[open]`, `[in progress]`, `[done <date>]`, `[deferred]`, `[OBE]`.
- When an epic ships, its stories and notes move to `EPICS-HISTORY.md`; only its **standing rulings** stay here. Narrative never accumulates in this file.
- **Epics are named, not numbered.** A story's handle is `slug.N` (e.g. `iscsi.5`), shown beside its title; handles are stable, titles may be refined. Bare numeric refs like `3.25` or `Epic 16` are story numbers in `EPICS-HISTORY.md`.
- Story format: *As a [user|dev|component], I want …, so that …*. Numbering is identity, not order. Roles: **user** = a PVE user with `Sys.Audit` on `/` (reads) or `Sys.Modify` (changes) — authorization follows PVE (ruling 2026-10-14); **dev** = prerequisite work with no user-facing deliverable; **component** = a UI/API consumer of another part.

## 2. Standing rulings (binding)

One line each. These are decisions, not history; the rationale is in `EPICS-HISTORY.md` under the epic named. A change that conflicts with one of these stops and gets discussed first. (`PRINCIPLES.md` and `DESIGN.md` sit above this list. Parenthesised numbers are `EPICS-HISTORY.md` stories.)

### Cross-cutting
- **Authorization follows PVE (operator ruling 2026-10-14, as ADOCK's).** Every GET needs `Sys.Audit` and every mutation needs `Sys.Modify`, the privileges PVE checks for its own disk and storage operations; a refusal is a 403 naming the privilege and the path; no ANAS roles. **Tiered by ANAS (operator 2026-10-15):** PVE's privileges are granular (a custom role may carry Sys.Modify without Sys.Audit), so wherever ANAS asks for Sys.Audit, Sys.Modify also passes — one shared comparison (`privilegeSatisfied`) at the gateway and the daemon backstop. PVE answers only the permission question; every act runs as root in anasd and the PVE user is carried for the audit record. ANAS makes no on-behalf-of calls to PVE's API — that model belongs to multi-tenant systems, which are not ANAS's scope (operator 2026-10-15); a future route that needs one gets the exact PVE privilege, not the tier. Lessons from ADOCK 15.3, which died on its first deploy: the check must work on a standalone node (no `.members` nodelist), every fail-closed path logs its reason, the parser is tested against a CAPTURED permissions reply, and a live smoke as root@pam and as an unprivileged `@pve` user gates the merge. *(code review 2026-10-14, Amplifier)*
- **Never build a scheduler.** systemd timers are the mechanism and **the units are the store** — with one caveat (live-proof F9): systemd garbage-collects a DISABLED unit's run history, so a disabled task has no durable last-run at all; status derivation reports `disabled` and the detail says history is not retained while disabled (`anas-repl-*`, `anas-snap-*`, `anas-backup-*`; `Persistent=true`; no second config source; the runner is a dumb conduit that POSTs the daemon job and exits truthfully). *(5.5, 16, 17)*
- **Task timers: removing any ANAS timer unit deletes its systemd stamp and failed state; orphan stamps of our prefixes are swept at daemon start** (ruling 2026-09-25, SCHEDULES-GT-16…21). A leftover stamp makes the re-created timer fire immediately (`Persistent=true` reads the stamp as a missed run); a stamp whose unit still exists is the missed-run heal and stays.
- **Point release = fixes + refinements of the release theme (operator ruling 2026-09-27).** A point release carries bug fixes on shipped features and refinements of existing functionality that do not change workflows in fundamental ways; no new workflows. The version number is a signal to administrators of how much re-testing a release asks of them: a minor bump triggers extended regression regimes, a point release is consumed easily — so the bump is chosen by whether users must re-test, not by feature count. Exposing a capability the underlying system already has through existing surfaces (dataset encryption through import and create, 2026-09-27) is a point release; a new workflow or menu is a minor and takes the bake day. The operator judges the boundary. Coordinator's standing recommendation, not a rule: a point release that touches a boot path still gets the bake-day proof matrix.
- **Retrospective per release; the 0.3.5 post-mortem's rulings (2026-09-24).** After each release (minor, or a point release cut for a shipped bug) a short retrospective inks process changes here. From 0.3.5 (log/special/dedup vdevs invisible for two releases, GitHub #66): (a) **a story's live proof covers the DISPLAY side of every state it introduces, on the shape the requesting user has** — when a layout is involved, ask them for `zpool status -j` (or the equivalent) and build that shape, not the convenient one; (b) **the topology zoo is standing test infrastructure** — one fixture + one stunt-node fixture verb per pool shape (data-only, mirror, raidz, each vdev class, by-id partitions, device names, file vdevs, multi-entry sections, in-use spare), run by every parser and consumer test and re-captured whenever the stunt node's ZFS moves; (c) **"healed by X" is proven per consumer**, never asserted from a grep; (d) **the final pre-release review executes** (default permission mode, the reporting user's layout named in the brief) — a static review is not a gate; (e) **the design pass cross-checks TrueNAS** wherever our functionality overlaps — what it exposes, which cases and layouts it handles, where it refuses — as an input to scope and to the shapes we must prove (internal only; public text still names no product, §"No product-name positioning").
- **The 0.4.0/0.4.1 retrospective's rulings (2026-09-27; rationale in the session memory).** Finds by finder across the cycle: the operator's Google Drive human pass found six things no proof had (paste scope, Run-now gate, progress past the ceiling, viewer layout, an own-client id typed into a field the form should not have shown, and the asks for Cancel and a run viewer); the seven-backend emulator matrix, run the day AFTER the 0.4.0 tag, found six shipped defects that became 0.4.1; the independent reviews found one wrong design premise (rclone's `speed` is a decaying average, so the stalled rule as designed could never fire) plus polish; the live proofs found the band-down 404 and the frozen-process stall blind spot; a deploy exposed the runner orphaned by a daemon restart; CI found a timezone-dependent assertion; two users brought #68 (reproduced in a day, fixed in 0.4.0) and #69. Operator's verdicts: local models are slow but reliable channels for development (went well); 0.4.0 needed more testing time before the tag (did not). Rulings: **(a) Bake day.** A minor release is tagged no sooner than one full day after its last feature commit; that day runs the whole live-proof matrix — the backend emulator profiles included — plus one independent review of anything not yet reviewed, and the human pass ends BEFORE that day. Point releases cut for a shipped-feature bug are exempt. **(b) A story's ground-truth block cites a capture.** Every fact in a story's *Ground truth* names its capture file or GT number; a premise written from memory (the viewer's `speed` field) is what the design pass exists to prevent. **(c) No wall-clock in assertions.** Tests build instants in UTC from fixed values; CI runs the daemon suite under a second, non-UTC time zone so a local-time construction fails in the pipeline, not on a user's clock. **(d) Backend-facing stories name their emulator.** A story that touches a cloud, S3, Azure, GCS or crypt path lists the fixture profile its proof runs against (`cloud-backends-fixture.sh`: s3/smb/webdav/ftp/azure/gcs/crypt); a backend with no emulator says so and is operator-gated. **(e) Release bump by key.** The version bump edits the five lockfile entries by key path, never by string replace, and the lockfile diff is checked before the release commit.
- **The 0.4.2 retrospective's rulings (2026-10-06; rationale in the session memory).** A point release cut for two user reports on 0.4.1's Datasets work (#70, #71) grew to four stories plus three fix batches and the four identity stories, with the tag held twice. Finds by finder: users brought #70, #71, #72 (already fixed from the operator's own nodes before it was reported) and #73; the operator's pre-tag deploy on a stable node found the export/import-unit gap (pools.r1) and a hand-written mount losing the boot race, shapes the stunt node cannot have; a fresh full-diff review found twelve cross-story danglers the per-story reviews missed; a fresh test review found sixteen gaps, the headline a product-wide parse of systemd timestamps that only worked in US and UTC zones; the whole-codebase identity audit found forty-seven findings, twenty of them destructive verbs keyed on a derived name; the second review lane caught a fix that had rewritten a test invariant (GT-7) and a fixture guard that read an ssh failure as absence. The operator's reading: bugs grow when code moves and the daemon is not clean enough internally to stop bleedover between stories; the cross-cutting review and the identity audit were judgment, not luck (destabilised code wants a whole-diff review; data is the most important thing). Rulings: **(a) The release gate is one fresh review of the whole release diff**, point releases included; per-story reviews stay, the final review is a fresh agent over everything since the last tag, before the release commit. **(b) A test invariant is a ruling, not a rewrite.** An agent whose fix changes what an assertion means stops and reports; the operator decides which side was right. **(c) Fixture guards fail loud.** A probe that cannot reach the node throws; absence is only ever a positive answer from the node. **(d) System timestamps are parsed in a forced zone.** Every call that reads timestamps from a system tool runs with `TZ=UTC` and `LC_ALL=C`, and its proof runs under CI's second zone; this extends the 0.4.0 ruling (c) from assertions to product code. **(e) Point-release scope ceiling.** A point release that grows past the stories it was cut for, or touches a destructive or boot path, takes the bake-day proof matrix while keeping its point number. **(f) One real node before the tag** is the standing final check, inked: the release build goes onto one of the operator's stable nodes before tagging, and the operator walks the screens the release touched plus any screen not yet on a test path. **(g) One thematic audit per minor release** *(amended 2026-10-14 by the 0.4.3 retrospective: whole-codebase reviews are human-initiated and reserved for a major release)* The design pass names a cross-cutting theme (identity in 0.4.2) for a fresh whole-codebase audit; findings are groomed, not necessarily shipped. **(h) The retrospective closes the cycle.** Its last step moves the cycle's shipped §3 sections verbatim to `EPICS-HISTORY.md`, archives the cycle's session-handoff entries, and re-checks the memory index for drift — §3 holds only active and open work, so every agent's fixed read (PRINCIPLES + EPICS + DESIGN) stays small; measured 2026-10-06: ~89k tokens per dispatch with the shipped detail in §3, ~49k without. **Watch item, not authorised:** if cross-story bleedover stays chronic, the answer is a single-responsibility refactor of the daemon's modules, raised at grooming with the retrospectives as evidence.
- **The 0.4.3 retrospective's rulings (2026-10-14; rationale in the session memory).** A bug release for #74/#75 and a pve5 incident: four stories, a full bake-day matrix, the fleet on it the same day. Finds by finder: users brought #74 and #75; the operator's human pass found the share-save dialog "getting complicated" (four stacked decisions); a real node found install-tree ownership wrong since 0.1.0; agents caught three errors in the coordinator's briefs; the bake day found a stdin hang, a create-then-destroy busy pool and that the matrix exercised no 0.4.3 story directly. Then the operator-ordered whole-codebase review (`docs/CODE-REVIEW-2026-10-14.md`) found three critical and eight high findings that no story review or cross-model lane had: story reviews read diffs, and the injections sat in old paths no diff touched. Rulings: **(i) One validator per file format, and `--` before operands.** Every user-supplied string that reaches an argv or a config file passes the one per-format layer in `shared/` (escape where the format has an escape, e.g. fstab `\040`; refuse where it does not); `--` goes before operands wherever the tool's parser honours it (checked per tool, not assumed); a reviewer of input-handling code constructs the hostile input and runs it. **(j) Jobs re-read and re-gate.** A job re-reads its object under a per-object lock and re-runs every request-time gate before it acts, through the one `safety/` helper (review H8). **(k) Tests gate the release.** `npm test` runs the shell and perl suites; `release.yml` publishes only a commit whose CI is green. **(l) Fakes print captured output.** A test fake answers with a captured PVE/system line from `fixtures/`, never a string the test author typed (ADOCK 2026-10-14: two live failures hidden by builder-shaped fakes). **(m) Dialog complexity is a design pass, outside point releases** — the share-save dialog gets one before it gains any further option. **Ruling (g) amended — whole-codebase reviews are human-initiated.** A whole-codebase review is reserved for a MAJOR release; a point release gets a review scoped to the paths it changed. Neither runs automatically (quota and other external factors): the coordinator reminds the operator at release planning and again before the tag, and when the release touches authorization, input handling into argv/config files, or a destructive path, the tag is gated on the operator's decision (run the scoped review, or waive it explicitly).
- **journald is forensics, never correctness.** Authoritative state comes from the system itself (ZFS/btrfs/md state, systemd unit + timer state, config files); journald supplies recent detail, labeled as such. No ANAS-written state files. *(5.5, 16, 17 stage 5)*
- **One menu per feature; actions live on the grid toolbar; detail windows are display-only.** No row-icon action columns. *(9, 11 refinement, 15.4)*
- **Dashboard shows only running ops (jobs strip) and failures/overdue (warning cards).** Healthy/idle shows nothing. Healthy AHR pools do get structural presence like ZFS pools (11.13). *(2, 5.5, 16.7, 17.7)* Telemetry leaf rows carry the same whole-disk by-id the Disks view lists: a kernel-named leaf (the device-named-pool shape, `sdb5`-style) resolves through the by-id listing to its parent disk, and a leaf nothing resolves keeps the name ZFS printed (0.4.1; the vdev row itself keeps ZFS's own name).
- **Notifications go through PVE's notification system only**, via the one `pve-notify.ts` client and shipped `.hbs` templates. Per-task `notify: always | on-failure`; **default `always` for backup (vzdump parity), `on-failure` for snapshots and replication**; skips never notify; bodies are plain ASCII facts with no commentary; delivery is best-effort and never fails the run. **Overdue is PULL (dashboard), never a push.** *(9.4, 11.4, 16.12)*
- **PVE territory is read-only and hands-off.** `storage.cfg` is parsed, never written; PVE-managed pools/datasets/mounts (and zvols) are tagged and untouchable; `/mnt/pve` is reserved; PVE's content-typed artifact-store paradigm is never replicated. *(3.25, 18)*
- **Version skew: additive, optional fields; warn, don't fail.** A new UI against an old daemon renders today's screen; the skew banner names the versions. *(12.1, 11.19)*
- **Secrets:** per-item root-only 0600 files under `/etc/anas/creds/` (mounts, PBS repos); **write-only through the API**; never argv, never journald, never inline in a config file. PVE-held secrets are read at exec time, never copied. *(16.2, 16.8, 18.5)*
- **Cluster-wide registries live in pmxcfs** (`/etc/pve/anas/*.json`, `/etc/pve/priv/anas/*`) with **CAS versioning** (`version`/`updatedBy`; 409 on a stale write). Per-node artefacts (mounts, tasks, units) stay local. *(5.5.2, 16.2, 18)*
- **Guide, don't just warn.** Busy errors name the holding processes (`busy-diagnosis.ts`, spans ZFS/AHR/mounts, fail-open); test-connection endpoints DIAGNOSE (dns / tcp / tls / auth / not-found) rather than fail; refusals say what to do next. *(3.29, 5.5.2, 16.6, 18.5)*
- **Safety altitudes:** 409 + confirm code for data-destroying ops; a hard 409 with no bypass for ops that are unsafe *now* (busy resilver/reflow, degraded array); an **advisory amber commit-gate** ("review to continue") for waste-not-loss — never block, warn-and-confirm. *(3.31, 11.6, 11.16, 3.30)*
- **A live initiator is never yanked (operator ruling 2026-08-26):** an iSCSI target with live sessions cannot be deleted (409, no bypass — log the initiators out first), a target can only be deleted once it has NO LUNs (delete them first; their backing stays unless `destroyBacking` is chosen per LUN), and a LUN in use by a session cannot be deleted. Disconnecting a client is not something to confirm — it is a state to refuse.
- **Parallel construction:** ZFS and AHR function alike; divergence only where the technology differs, and then stated in the UI. Sanctioned divergences: md keeps no scrub completion record (honest absence); AHR scrub has no Stop; AHR members are partitions (full by-id shown, never truncated). *(11.18, 17 stage 5/6)*
- **Ground truth first:** capture real command output before writing a parser; fixtures are labeled real capture vs synthetic; live-prove on the stunt node (including failure paths) before release; never against the operator's real PBS/TrueNAS. **A mutation job that runs two or more system commands in sequence is live-proven on the stunt node as a matter of course, success AND each failure step, before it ships** (ruled 2026-09-20 after #60: the fake executor cannot know that `smbpasswd -x` depends on the account `userdel` just removed, and it cannot catch a fall-through where a failed step is reported as success — the unit test asserted the wrong order and passed). A unit test proves the argv; only the stunt node proves the sequence. *(every epic)*
- **Dialog ↔ daemon contract:** for every option, value / `null` / omitted mean set / clear / keep; an untouched edit rewrites byte-identically (pre-fill reflects the entry exactly, never field defaults); fields are read by itemId, no hiddenfield mirroring. *(#34, #43, #26)*
- **Structured output only** (`-j`, `--output-format json`); never parse human tables when a structured form exists. *(Principle 13)*
- **Ids are never truncated; numbers carry labeled context.** *(11.18, 15.6)*
- **Design pass = mechanism AND workflow, equal weight (operator ruling 2026-09-21).** A §3 slate entry is authorized SCOPE, not a dispatchable story. Each item first gets a design pass in its design doc, and from that pass the concrete numbered stories are cut — those are the dispatch unit. The pass answers, beside the commands / ground truth / failure model: **where it lives** (the one menu or panel and the entry action); **the happy path as the user sees it**, screen by screen, every number labeled, every state derived from the system; **timeliness** — what the user sees during a job, what refreshes when it completes or fails, and how stale a screen may be before that is a defect (0.3.3: delete grids that did not reload on failure were a workflow bug on a correct fix); **failure as the user meets it** — which refusal appears where, what the guiding text says, and the recovery verb offered on the same screen; **proof** — a Playwright spec per workflow beside the live proof of the mutation steps. Correctness and robustness are the pillars; the workflow is the only place a user ever meets them.

### ZFS — pools, datasets, snapshots *(Epics 3/4/5)*
- Shares are storage-agnostic: **a path is a path** (smb.conf / exports edited directly, never `sharesmb`/`sharenfs`); only filesystem datasets are shareable. *(DESIGN §5a)*
- Pool root dataset is first-class on ANAS-managed pools; view-only on PVE-managed ones (a recursive root snapshot there would sweep PVE's zvols). *(3.26)*
- Special/dedup vdev redundancy is **enforced**, not advised; `special_small_blocks` exposed. *(3.22)*
- **One disk per attach**; RAIDZ expansion gated on OpenZFS ≥ 2.3.0 + `feature@raidz_expansion` (guiding 409); honest realized-capacity estimate shown; `autoexpand=on` default at create; `zpool online -e` after a larger-disk replace (never flip a pool's autoexpand). *(3.31)*
- No default pool name; mountpoint is a ZFS property, never fstab; the same collision checks as AHR. *(3.27, 3.28)*
- Permissions editor is **POSIX ACLs** (`acltype=posixacl`, `acl` package); NFSv4 ACLs deferred to Epic 14. *(4.7.2, 4.7.1)*
- Dedup lives behind an advanced, RAM-cost-stated control; `sync=disabled` carries a data-loss warning. *(4.10, 4.12)*
- Dataset encryption: deferred until a user asks (key management is the work; PVE has no precedent). *(4.11)*

### Replication *(Epic 5.5)*
- Remote needs **sshd + ZFS only** — nothing is ever installed there; push-only; TrueNAS works as a target.
- Two peer tiers: cluster peers auto-discovered from `/etc/pve/.members`; external remotes registered. One cluster-wide keypair at `/etc/pve/priv/anas/replication_key`; pinned host keys, fingerprint confirmed once (no silent TOFU).
- Destination `readonly=on` by default; `recv -F` behind the confirm gate; a FULL send is announced with its size; **`zfs hold` on the incremental base**; the newest common snapshot IS the durable record. `zfs allow` delegation is a noted follow-on, not faked.

### Shares & identities *(Epics 6/7/8)*
- **A share on a PVE directory-storage path (e.g. `/var/lib/vz`) is allowed — caveat emptor** (ruled 2026-09-22). Shares are a path (§5a); the user typed it, ANAS never places anything there by default, and mounts/restore keep refusing storage.cfg paths. Shares on a PVE-OWNED ZFS dataset (storage root, guest volume, dir storage on a dataset) ARE refused — that is the footprint rule, not this one.
- Surgical config editing with comments/order preserved and byte-identical round-trips; `reload smbd` / `exportfs -ra` are side effects of mutations, never separate calls; an SMB interface-binding change is confirm-gated when clients are connected.
- Identities resolve via **`getent`/nsswitch, never `/etc/passwd`** (the Epic 14 seam). ANAS-created users are nologin share users (`useradd -M -s nologin`), never PVE users; `user.cfg` is never written. **User and group delete are IN, confirm-gated** (shipped by identity.1; ruling amended 2026-10-14, replacing "user delete is OUT"). Disable stays the default primitive, and **a deleted id must never be handed to a new user**: `useradd` gives a new account the highest uid + 1, so deleting the top user lets the next one inherit every file and ACL grant still keyed by that number (review M6 #25). System accounts (uid/gid 0, < 1000, 65534) are never mutable. Unresolved owners are flagged, not hidden.

### AHR — ANAS Hybrid RAID *(Epic 11)* — design: `AHR-DESIGN.md`
- Stack: size-matched partitions → **one md array per band (RAID5 = AHR-1 / RAID6 = AHR-2; redundancy lives here)** → LVM concatenation → **btrfs as the filesystem, never btrfs-RAID5/6**. ext4 dropped. No tier conversion.
- Fresh-create banding ≠ expansion: existing bands are immutable constraints; grow with ≥ the largest disk; backup-file-free reshapes only; resume = recompute-and-continue with only the approved disk set persisted; `mdadm --replace` for live replace; arrays carry `--bitmap=internal` (re-add rides it).
- Spares are full-coverage only (partial refused with the exact shortfall); md owns automatic failover; promote-to-member and shared spares OUT.
- Snapshots: `@data`/`@snapshots` subvolume layout; rollback preserves the replaced state as `pre-rollback-<ts>` and destroys nothing; flat pre-layout pools report `subvolLayout:false` with **no in-place migration** (destroy/recreate is the migration).
- Notifications discriminate check vs rebuild (`last_sync_action`, bad-block list); **recommend a scrub, never enforce one**; auto-scrub-after-rebuild rejected.
- Everything keyed by-id/UUID; device names resolved at point of use.
- **Cache tier = lvmcache `--type cache` in WRITETHROUGH only** (read cache; GitHub #63, ruled 2026-09-21). Writeback and `--type writecache` are rejected: dirty blocks exist nowhere but the SSD, a cache-device loss loses data, and both cross the self-heal boundary (repair reasons at md, below LVM). A writethrough cache never holds the only copy, so a missing cache device is dropped automatically at boot (`--uncache` + `vgreduce --removemissing`) and the pool comes up uncached — no data at risk by construction.
- **iSCSI LUN image files on AHR stay copy-on-write** (ruled 2026-09-11): no `NOCOW`/`chattr +C`, no per-LUN toggle. NOCOW drops the btrfs data checksum for exactly the object where corruption is hardest to notice, puts it outside scrub attribution and self-heal, and snapshots (every backup run, every schedule) defeat it anyway — first write after a snapshot is CoW-once, so the file fragments regardless. Guidance is placement, not a flag: random-write block workloads → zvol. Reopen only if CoW proves harmful generally, never for one workload.

### Backup via PBS *(Epic 16)*
- A task = repository ref + namespace + **`backup-id`** (explicit, logical; hostname only the default) + **1..N archives** `{name, path, excludes[]}` — names/paths are explicit config, never derived. Excludes are config, `.pxarexclude` is respected.
- Repositories: two tiers — **PVE's `pbs` storages auto-discovered** (secret read from `/etc/pve/priv/storage/<id>.pw` at exec, never copied; PVE-badged, not editable) and ANAS-registered ones (token recommended, password supported; fingerprint pinned with one-time confirmation).
- **ANAS never contacts the PBS server for status or monitoring.** Sanctioned contacts: the backup run itself, the explicit repository Test, the save-time namespace verify, the post-success prune and its user-initiated preview — and, from phase 2, **user-initiated restore operations** (snapshot listing for a restore, `catalog shell` browsing of an archive, the restore itself). Never polling, never background. Server-side history/verify belongs to the PBS UI.
- Run Now goes through the task's own unit (one code path, one history). fd cap via `prlimit --nofile` around the client exec (per-task, default 1024).
- Cadence: weekly / **biweekly with EXPLICIT ISO-week parity** / monthly / custom OnCalendar; an off-week fire is a visible `skipped (off week)` (exit 75, unit success); heal rule: run regardless when the last success is > 14 days old; Run Now bypasses the gate; overdue is cadence-aware.
- Retention: absent policy ⇒ ANAS never prunes; prune runs after a SUCCESSFUL run with exactly the configured `--keep-*`; a prune failure never fails the job (warnings); **GC stays PBS-side**.
- `--change-detection-mode` is a per-task choice with honest guidance. Client-side encryption is a v1 non-goal (door left open via the env contract).
- Mounted drives and any path are first-class sources; snapshot-consistency is a **per-source capability** (phase 2 builds it — until then every backup is a live backup, and the UI must say so).

### Cloud sync via rclone *(rclone.1–3, GitHub #57)* — design: `DESIGN.md` "Cloud sync — rclone"
- **rclone as it is:** Debian's `rclone` (1.60.1 on PVE 9) is a hard dependency installed by `install.sh` like samba; no supported newer path exists (no backports entry, upstream = bare `.deb` without a signed repo — checked 2026-09-23), so a newer rclone is the operator's manual install and is used unchanged; NO cloud-vendor code, NO two-way sync, NO restore UI (copy-back is the operator's `rclone copy` on the node), NO retention/versioning on the remote, NO dry-run endpoint.
- **Remotes are ANAS's own `/etc/anas/rclone.conf`** (0600 root, per node), passed explicitly on every call with `--ask-password=false`; root's default `~/.config/rclone/rclone.conf` is never read or written (operator ruling 2026-09-23: a file root edits independently is not a store ANAS controls; copy-back names the file with `--config`); a password-protected file is reported and refuses mutations. ANAS writes the INI section itself (secrets obscured through `rclone obscure -` on stdin — **never argv**, the iSCSI ruling), then gates on `rclone config dump` with a byte-identical rollback. Secret values are never returned (`secretsSet[]`); a secret is `IsPassword` or a key ending in `pass`/`password`/`secret`/`token`/`key`, never a `bool` option.
- **The remote dialog renders from rclone's provider schema** (basic options + an advanced toggle, provider-filtered rows, OAuth by pasting `rclone authorize` output) — the generic form is what keeps "any backend" true without vendor code; a curated subset would be vendor code.
- **Tasks are `anas-cloud-<name>` units** on the one unit-store helper; cadence, runner, Run-Now-through-the-unit, status derivation, supervision and overdue are backup's, **extracted into a prefix-parameterised shared module — not copied**. Notify default `always` (backup parity).
- **Run guards:** source must exist; a configured-but-unmounted mount is refused (the backup2.11 guard, built ONCE here as a shared helper); `sync` with an empty source is refused ("would delete everything at the destination"); `copy` is the default mode and never deletes. Source consistency is derived as backup derives it (transient snapshot on ZFS / layout AHR, live elsewhere, labeled); nested filesystems are not included and the dialog says so before save.
- **Exit codes:** only rclone `0` and `9` complete; `6` (some files failed) fails the run — missing files at the destination are a failure, not a warning. Verdicts for Test come from rclone's message text (every `NewFs` failure exits 1), with `error` + the text as the honest fallback.

### Schedules — snapshots & scrubs *(Epic 17)* — design: `SCHEDULES-DESIGN.md`
- ANAS manages snapshot schedules itself (sanoid dropped: ZFS-only, could not be uniform across AHR): one timer per schedule, keep-N bucketed retention, `zfs snapshot` / 11.12 btrfs primitives underneath.
- **Retention respects holds:** held snapshots are excluded up front, re-checked before each destroy, and surfaced as `skippedHeld` — skip-and-surface, never try-and-warn.
- Scrubs stay filesystem-native and are **surfaced + toggled, never double-scheduled**: ZFS = `org.debian:periodic-scrub` property (PVE's monthly cron); AHR = mdcheck timers (node-global, stated). Last scrub: ZFS from `zpool status` scan stats; AHR honest absence. Run/Stop are second doors to the existing verbs; Stop is ZFS-only.

### Mounts *(Epic 18)*
- **Remote NFS/CIFS only** (`MountType` = nfs|cifs; the daemon 400-rejects mutations on local filesystems). Local/removable drives and single-disk formatting are not ANAS's problem — a local disk's path into ANAS is a ZFS pool or an AHR pool.
- Pure management: ANAS writes fstab and calls `mount`/`umount`; the systemd fstab generator does the work; configured = the fstab line, actual = `findmnt`. `nofail` forced; boot mount is the default, automount a per-mount toggle.
- **The hang trap:** the daemon never touches a mountpoint synchronously — liveness via `timeout 2 stat -f`; an armed automount takes its identity from its fstab entry.
- Verb ladder: *unmount* (kernel state now) / *disable* (credentials kept, byte-identical re-enable) / *delete* (entry + credentials gone). **Disable is `noauto` + `x-anas.disabled` on the live line (rulings 2026-10-14):** the `#ANAS <verbatim>` marker is a marker comment (Principle 12) and a hand edit that removes it activates the mount. `noauto` alone cannot carry it — it is already the operator's own "enabled, not at boot" toggle — so disable adds `noauto,x-anas.disabled` to a line without `noauto`, and `x-anas.disabled=kept-noauto` to a line that already has it; re-enable removes exactly what disable added, so the line comes back byte-identical. `x-*` is fstab's documented namespace for application options (systemd and mount ignore it); a hand edit that removes it leaves `noauto`, so the mount still does not come up at boot. Existing `#ANAS` lines are read as disabled and left alone; a line is rewritten to the new form only when ANAS next changes it (re-enable, edit, disable again). No bulk migration. **Automount lines (ruling 2026-10-14, after the node pass):** `noauto` does not stop systemd-fstab-generator arming an `x-systemd.automount` line, so Disable also swaps `x-systemd.automount` IN PLACE to `x-anas.disabled-automount` (Enable swaps it back — the line stays byte-identical), and Disable and Remove stop the line's `.automount` unit before the daemon-reload. Options: structured common tiers + verbatim passthrough for the long tail.
- Mountpoint must be an empty dir, never under `/mnt/pve`; unmount cross-checks shares and backup tasks riding the path.

### UI & packaging *(Epics 13/15/10/12)*
- Native ExtJS panels injected into the PVE UI (Ceph model); `anas` is a pure API gateway forwarding `/api/nodes/<node>/v1/*` with the user's ticket over cluster-CA TLS; served through PVE's `:8006` via a fail-open pveproxy hook (`PROXY-TRANSPORT-DESIGN.md`). Fail-open everywhere: a broken ANAS never breaks the PVE UI.
- `ANAS.gfx` is the one shared visual layer: SVG + DOM (never canvas), disk/vdev objects, gauges, drag toolkit, `timeChart` (**1-2-5 binary ladder + ratchet-up-only, operator re-fit, single-vdev collapse with member tiles never collapsed, labeled short-window averages, hatched unsampled region**).
- Distribution is the release tarball + transactional `install.sh` (preflight → install → health → rollback on failure); dependencies an ungated feature needs are installed (samba/nfs/mdadm/btrfs-progs/acl…); semver has one source (`bump-version`); **releases are cut by the Actions workflow on a `vX.Y.Z` tag and always carry hand-written notes**. No yaml config layer; overrides are env/unit drop-ins.

- **Host configuration backup (operator idea 2026-09-27; "Proxmox nodes are supposed to be disposable, but in practice that's not usually true because of devices and network config"):** what a node carries that a reinstall does not give back: `/etc/network/interfaces` and the bridges/bonds/VLANs, `/etc/hosts`, DNS, `/etc/fstab` and the mounts ANAS wrote, `/etc/modprobe.d` and vfio/passthrough ids, `/etc/default/grub` and kernel parameters, udev rules, `/etc/mdadm/mdadm.conf`, `/etc/lvm`, the ZFS cache file, `/etc/samba`, `/etc/exports`, LIO's saved config, `/etc/anas` (rclone config, backup repos, creds), `/etc/pve` (pmxcfs: storage.cfg, user.cfg, firewall, guest configs — the cluster database at `/var/lib/pve-cluster/config.db`), `/root/.ssh`, cron and systemd overrides, and the apt selections. **Cross-check (facts, ProxMenux docs 2026-09-27):** its host backup is an rsync of `/etc`, `/etc/systemd/network` and `/root` plus a sqlite snapshot of `/var/lib/pve-cluster` and optional paths; a JSON manifest of hardware, kernel parameters, network layout, ZFS state, users and cron; the list of manually installed apt packages and component versions; three destinations; restore reads the manifest, diffs source against target, replays the filesystem and reinstalls components against the target's kernel, merging user tuning across kernels; explicitly not a guest backup. **Our shape, if built:** no new engine — a preset backup task in the existing Backup menu whose source is the curated host surface above (PBS `host` backup type, so the snapshots dedupe and live under the node's own retention like every other ANAS backup), a manifest file generated at run time into the archive (the facts a diff needs: disks by-id and their roles, pools, network layout, kernel parameters, package selections, ANAS version), and a **restore that never overwrites the live host**: restore into a directory and present the diff against the running node file by file ("this is what the old node had that this one does not"), the operator applies what they choose — guest philosophy at its strongest, and the honest answer to cross-kernel and cross-hardware moves. **Storage (operator 2026-09-27):** PBS is the store, and an **exportable artifact** is the alternative — the same archive and manifest written as one self-contained file (a tarball the operator downloads from the UI or the task writes to a path or a cloud sync remote), for the case the idea comes from: a dead or replaced node whose PBS is not reachable from the rescue shell yet. Synergy with the parked DR project (the manifest is the protection inventory's node half). **Open calls before any story:** the exact file list and what is deliberately excluded (secrets: `/etc/pve/priv`, ssh host keys, ANAS creds — included but flagged, or excluded), whether the cluster database goes in as the sqlite file or as `/etc/pve` files, how PBS's `host` type presents in the existing restore picker, and whether the diff view lives in the Backup menu's restore flow or in a Node page. Candidate; not authorized; design pass first.
- **Local-snapshot file restore** *(decoupled from Backup phase 2, 2026-08-25)*: the `backup2.5` picker over `.zfs/snapshot/<s>/` and AHR ro snapshots, copying selected files back without a rollback. No backup client involved — "just files". Its own small epic when wanted.
- **Ceph RGW / S3**: surface the object gateway PVE installs but never exposes — ANAS's purest "thing PVE doesn't do". Candidate epic.
- **Lean HA / event-driven replication**: near-term, replication triggered off the ZFS `written` counter (idle disks stay asleep); later, a 2-node quasi-HA without Ceph (SMB msdfs, NFS keepalived VIP) — async, bounded RPO, never sold as true HA.
- **Policy-based tiering (3.24)**: scheduled, auditable data movement between fast and capacity tiers inside a pool. Own epic; the vdev/composer work is its prerequisite. GitHub #65 (2026-09-22) asked for DSM-style hot/cold tiering to keep archive disks asleep — on BOTH pool types; answered 2026-09-23 as not planned (caches answer the hot-data half on ZFS, `ahrcache.1` on AHR; nothing keeps a cold read from spinning the pool up). Demand signal: one.
- **Dataset encryption (4.11) — ASKED (GitHub #69, 2026-09-27, a TrueNAS migrant with encrypted pools who wants unlock + key persistence across reboots; reply posted asking key shape and encryption-root scope):** promote at the next grooming. Scope facts settled with the operator 2026-09-27: ZFS native encryption has two key formats, `passphrase` and `raw`/`hex` (one 32-byte key, two spellings) — BOTH must work, since TrueNAS offers either per dataset and a migrant arrives with whichever they chose; three keylocations — `prompt` (passphrase datasets; unlock feeds it on stdin), `file://` (persistence; TrueNAS hex exports land here) and `https://`/`http://` (OpenZFS 2.2+, fetched at load — allow, do not build around); GELI (TrueNAS CORE pre-native) is OUT, not importable on Linux. Design shape to pass: keyfiles under an ANAS-owned 0600 directory with `keylocation` set on the encryption root, a boot unit loading keys after `zfs-import` and before anasd/samba/nfs (PVE ships no auto-unlock; `zfs-mount.service` loads no keys), Datasets shows a locked marker with Unlock… (passphrase or stored key) and "remember on this node"; change-key and unload later. **Surface constraint (operator 2026-09-27):** this is a boot-time behaviour PVE itself does not expose, so it is highlighted explicitly in the release notes under its own heading — and its surface is limited: the key-load unit is INSTALLED only when the first key is remembered on the node and REMOVED when the last one is forgotten, so a node without stored keys (every existing ANAS user) boots exactly as before; nothing changes for anyone who does not use encryption. Security frame: root-on-node = game over; a key on disk is what TrueNAS does.
