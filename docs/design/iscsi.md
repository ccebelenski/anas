# iSCSI

## iSCSI — block storage (iscsi epic; designed 2026-08-25, ground truth `docs/ISCSI-GROUND-TRUTH.md`)

ANAS is the **target side only** — a generic iSCSI target on LIO (kernel target) driven by `targetcli-fb`; PVE and guests are ordinary initiators and `storage.cfg` is never written. Identity: a target is its URL-encoded IQN; a LUN is its index `n` within the target. Two backing kinds: `zvol` (ZFS) and `file` (a sparse raw image on a dataset or AHR pool — AHR's only kind). Read model = `saveconfig.json` (persisted) + configfs (live); writes = one `targetcli` command per invocation (stdin batching always exits 0 and autosaves half-applied state) behind a daemon mutex, then `saveconfig`.

| Method | Path | Description | Response |
|--------|------|-------------|----------|
| `GET` | `/v1/iscsi/targets` | All targets on the node: ANAS-managed (ownership derived from the backing path + naming, never shadow state) and foreign ones tagged hands-off; per target: portals, LUN count, session count, enabled, health. Every TPG of a target is read: sessions of every TPG, the LUNs and portals of the TPGs after the first under `otherTpgs`. A session state that could not be read sets `sessionsUnknown` (the count is then a floor and every session gate refuses, `sessions-unknown`); configfs directories that exist and could not be listed are named in `configfsUnreadable` | `200` |

The auto-added `0.0.0.0:3260` portal is removed; `demo_mode_discovery=0`, `generate_node_acls=0` | `202` with job |
| `GET` | `/v1/iscsi/targets/:iqn` | Detail: portals, LUNs (kind, backing, size, **serial**, attributes), ACLs (`credentialsSet`, never the secret), live sessions (from `acls/<iqn>/info`), restore holes (saveconfig ⟷ configfs diff) | `200` |
| `PUT` | `/v1/iscsi/targets/:iqn` | Edit portals / ACLs / auth (rotate secrets: written to configfs, never argv) | `202` with job |
| `DELETE` | `/v1/iscsi/targets/:iqn` | Delete an EMPTY, session-free target only (operator ruling 2026-08-26): live sessions → `409`, no bypass, listing the initiators ("log them out first"); any LUN still mapped → `409`, no bypass ("delete the LUNs first" — each LUN delete keeps its backing unless `destroyBacking`); no confirm code on this route any more | `202`/`409` |
| `POST` | `/v1/iscsi/targets/:iqn/state` | `{action: enable\|disable}` — TPG enable flag; `disable` is also the entry gate a LUN restore uses | `202` with job |
| `POST` | `/v1/iscsi/targets/:iqn/luns` | Add a LUN: `{name, kind: zvol\|file, backing}` — `zvol` names an existing ANAS-managed volume (PVE `vm-*` zvols never eligible); `file` names a dataset or AHR pool + `size` and creates the sparse image. `name` is the SCSI model string initiators see (validated). ANAS sets `emulate_tpu=1`, `emulate_tpws=1`, `max_unmap_lba_count`, fileio `write_back=0`; `block_size` chosen here (immutable once mapped); serial generated and stored | `202` with job |
| `GET` | `/v1/iscsi/targets/:iqn/luns/:n` | LUN detail incl. serial, attributes, connected initiators, backup/restore eligibility | `200` |
| `PUT` | `/v1/iscsi/targets/:iqn/luns/:n` | Resize (zvol: live grow — **allowed under a live session**, the initiator rescans, same rule as the Datasets door; file: delete + recreate replaying **serial and attributes** — refused under a session; shrink always refused), attribute changes (`write_back` behind a warning, refused under a session) | `202`/`409` |
| `DELETE` | `/v1/iscsi/targets/:iqn/luns/:n` | Unmap + delete backstore; `?destroyBacking=true` also destroys the zvol/image behind the confirm gate, in the order unmap → delete backstore → `saveconfig` → destroy, so a destroy that fails afterwards fails the job with `LUN <n> deleted, backing kept: <reason>` and leaves no restore hole; `destroyBacking` on a backstore another LUN also maps is refused (`backstore-shared`), and without it only this LUN is unmapped and the backstore is kept; a LUN in use by a live session → `409`, no bypass — per LUN, via each session's `mappedLuns` (operator ruling 2026-08-26) | `202`/`409` |
| `GET` | `/v1/iscsi/sessions` | Every live session on the node (initiator IQN, target, LUNs, addresses) — the cross-feature gates and the dashboard read this | `200` |
| `GET` | `/v1/iscsi/claims` | Every backing path currently mapped as a LUN (`{path, targetIqn, index, kind}`), and every backing held by a backstore no LUN maps (`unmapped: true`, no target or index) — the ONE call Pools/Datasets/AHR/Mounts ask "is this held by a LUN?" (`iscsi.6`) | `200` |
| `GET` | `/v1/iscsi/health` | saveconfig ⟷ configfs diff (LUNs whose backing device was missing at restore, portals bound to addresses no interface carries, foreign changes, `targetsServingNothing` = targets restored with none of their saved LUNs, `stubLuns[]` = fileio placeholders the restore service created (quarantined on read), `disabledTargets[]`, `unmappedBackstores[]` = backstores no LUN maps (never `degraded`, blocks nothing), `restoreMarks[]` = LUNs whose whole-image restore is running, was interrupted, is unverified or whose mark is unreadable, `degraded`) — feeds the `iscsi` dashboard warning category | `200` |
| `POST` | `/v1/iscsi/health/repair` | Re-create the LUNs a boot restore dropped as a **surgical `targetcli` replay of the persisted record** (`wwn=` + attributes + the stored index + ACL re-grants) — NEVER `targetctl restore`, whose rtslib default `clear_existing=True` wipes every live target and session; `409` while any backing device is still absent (naming them); `saveconfig` only after a repair that left no holes, and none when there was nothing to do. A hole in a foreign target, or in a target ANAS keeps its hands off (below), still degrades the node but is never written to: Repair plans it blocked and answers `409` (`foreign-holes-only` / `target-hands-off`) when only such holes remain; its result names them (`foreignUntouched`, `stillDegraded`) | `202`/`409` |

`GET /v1/iscsi/targets` also carries `nodeInitiatorIqn` (this node's own initiator name from `/etc/iscsi/initiatorname.iscsi`, `null` when unknown — additive) so the ACL editor can offer **Add this node**; and because discovery is closed to unlisted initiators, **a create with an empty ACL list is refused with a guiding 400** (an edit that removes the last ACL is allowed but warns on the job) — an operator finding from the first real-node round. Every iSCSI read carries an **availability envelope** (`installed`, `configfsPresent`, `saveconfigPresent`, optional `reason`) around its payload — "LIO not installed" is a first-class, non-error state (fail-open ruling). `IscsiHealth` also carries `degraded` (true whenever the live tree lacks something the persisted config has — the guard that blocks any `saveconfig`) and `interfacesUnknown` (fail-open when `ip -j addr` fails). `GET /v1/iscsi/targets/:iqn` answers `404` for an unknown IQN and `400` for a string that is not an iSCSI name. **Hands-off rule** (`handsOffRefusal`, one predicate for every mutation verb and for Repair): ANAS changes a target only when it owns it (`foreign-target` otherwise), when it has a single TPG (`multiple-tpgs`: ANAS creates one TPG per target and does not change a target given more by hand), and when no LUN's backing ownership is unknown (`backing-ownership-unknown`: a failed `zfs list` leaves a file backing's dataset, and whether PVE owns it, unknown; such a backing is never read as foreign or as absent). A `saveconfig.json` that exists and cannot be read (`saveconfig-unreadable`) or a configfs directory that cannot be listed (`configfs-unreadable`) degrades the node and refuses every iSCSI change and Repair, since each ends in a `saveconfig` that would overwrite what could not be read. **IQN convention** (shared `anasIqn`/`isAnasIqn`): authority = reverse(`anas.` + the node's FQDN-or-hostname) — `iqn.<yyyy-mm>.com.example.nas.anas:<name>` for `nas.example.com`, `iqn.<yyyy-mm>.nas.anas:<name>` for a domainless `nas` (live-proof F1: rtslib rejects any authority without a dot — `iqn.2026-08.anas:x` → `WWN not valid as: iqn`; the hostname label also keeps two domainless nodes from colliding). Recognised by the authority's last label being `anas`, deliberately date- and domain-agnostic so a stateless node never has to remember either; `IscsiIqn` refuses an authority with fewer than two labels, mirroring rtslib. A block backstore's size is not in configfs; it is read from `/sys/class/block/<kernel>/size` with the kernel name resolved at point of use and never stored.

**PVE footprint ownership (pvepool.1, designed 2026-09-21 — GitHub #61).** Story 3.25 tagged a whole ZFS pool as PVE's when any `zfspool` storage named it. PVE's real footprint is smaller and is read from `ZFSPoolPlugin.pm` (PVE 9.2.20, verified on the stunt node and pve5): the storage's configured `pool` path — which may be a nested dataset such as `rpool/data` — plus that path's DIRECT children whose names match `^(vm|base|subvol|basevol)-\d+-\S+$` (`zfs list -d1` + that regex is the whole inventory; `alloc_image` enforces the `vm-<vmid>-*` / `subvol-<vmid>-*` prefixes; status is `zfs get available,used <path>`; activation is a blanket `zfs mount -a`; `path()` derives `/dev/zvol/<path>/<name>` or `<mountpoint>/<name>`). Everything else on the pool is invisible to PVE. The relaxed rule: **ownership is per dataset, decided by ONE shared pure predicate, and pool-level actions on a PVE pool stay hands-off** (managing a PVE pool as a whole is a ruled no, #61).

- **Model.** `pveOwnership(refs: PveStorageRef[], dataset: string, system?: SystemPoolFacts): PveOwnership | null` in `@anas/shared`, where `PveOwnership = { storage: string, kind: 'storage-root' | 'guest-volume' | 'dir-storage' | 'system', reason: string }`. Owned when: (a) `dataset` IS a zfspool storage's configured path (`storage-root` — the pool root itself when `pool` is the bare pool name); (b) its parent is a storage path and its basename matches the guest regex (`guest-volume`); (c) it lies under the dataset a `dir` storage's `path` resolves onto (`dir-storage` — 3.25's deferred secondary signal, now in: PVE writes backups/ISOs/templates there; `parsePveStorageCfg` already resolves it via `matchMountpoint`); (d) system pool facts mark it (below). **Ownership is inherited by the whole subtree** of an owned dataset (a guest subvol's children, a dir storage's tree). Everything else — `rpool/ROOT`'s siblings aside — is ANAS-manageable, including new children of a storage root. The predicate is pure over `(refs, name)`; it never lists children, so daemon and UI compute identical answers from the same payload. It replaces the four daemon `isPveManagedPool` copies and six UI `isPveManaged` copies (single source of truth), and `PVE_GUEST_VOLUME_RE` in `iscsi-ownership.ts` is corrected to the plugin's regex (today it lacks `basevol-` and demands a `-disk-<n>` tail, so `subvol-100-foo` and every `basevol-*` slip through).
- **System pool (new hazard the relaxation opens).** On the default ZFS-root installer layout `local-zfs` is `rpool/data`, so a footprint-only rule would expose `rpool` (the root dataset), `rpool/ROOT` and `rpool/ROOT/pve-1` as manageable. `SystemPoolFacts` = `zpool get bootfs` per pool + the dataset `findmnt /` reports; on a pool with `bootfs` set or hosting `/`, the boot dataset, every ancestor up to and including the pool root, and the boot dataset's parent's WHOLE subtree (`rpool/ROOT/*`) are `system`-owned; **pool-level destructive ops on a system pool (destroy, export, change mount) are refused hard, no confirm bypass**; siblings such as `rpool/media` are ordinary datasets (a default install already keeps `rpool/ROOT` beside `rpool/data`). Neither test node boots from ZFS, so this gets a loop-pool ground truth with `bootfs` set.
- **Naming guard.** ANAS refuses to create, rename or clone a dataset whose basename matches the guest regex as a direct child of a storage path — PVE would inventory it as a guest disk on its next `list`. Validated in the dialog (field-level, before submit) and at the daemon (400, the backstop).
- **Consumers, re-examined.** *Pools* (grid, detail, `PUT /mountpoint`): unchanged — Export / Destroy / Add-vdev / Attach / Modify / Change-mount stay disabled on a PVE pool (badge tooltip names the storage AND now says datasets outside PVE's footprint are manageable). *Datasets*: per-node `pve?: PveOwnership` (additive, optional) on `DatasetNode`/`Dataset`; the storage root is view-only for props / share / snapshot / destroy (3.26's reasoning holds — a recursive root snapshot sweeps guest zvols) but **Create child is enabled on it**; guest volumes and dir-storage trees are view-only with Detail; every other node is fully manageable. *Snapshot schedules* (`routes/schedules.ts`): refuse only owned targets, not the pool; a recursive schedule on a storage root stays refused. *Replication target* (`replication-target.ts`, `routes/replication*.ts`): refuse only when the target dataset (or the child it would create) is owned or trips the naming guard. *iSCSI* (`iscsi-ownership.ts`, `iscsi-mutate.ts`): `foreign` / refusal only for owned backings (`backing-pve-guest-disk` keeps its text; `backing-pve-storage` becomes the storage-root / dir-storage case; the `pve-managed-pool` refusals go). *Backup consistency* (`backup-consistency.ts`): `live` downgrade only for owned sources; siblings get the normal snapshot; `lun-sources` hides only owned LUNs. *Mounts* and *file restore* are path-based already (`pveStorageFor`, `pveTerritoryReason`) — unchanged. **Version skew, fail-safe direction:** an old daemon omits the per-node `pve` field; a new UI that sees `pveStorages[]` non-empty on the pool AND no per-node field keeps the whole-pool rule — skew may only ever tighten, never loosen, a hands-off gate.
- **Workflow (equal weight — §2 rule).** *Where it lives:* Datasets menu, no new screen. *Happy path:* the tree shows the PVE pool with a badge "PVE storage root: local-zfs"; its guest volumes carry the PVE badge, greyed row, Detail only; a sibling such as `rpool/media` renders as any ANAS dataset. Create dataset → the pool picker now lists PVE pools → picking one shows an INFORMATIONAL note (blue, not a warning): "Guests on this pool share its I/O; PVE's free-space figure for `local-zfs` shrinks by what ANAS uses here." → name field validates the guest pattern live → job → on completion the tree reloads with the new node selected; on failure the tree reloads too and the toast carries the daemon's sentence. Share / Snapshot / Replication / Schedule / add-LUN pickers list the sibling datasets and omit owned ones. *Timeliness:* ownership is computed server-side per request from storage.cfg and the live dataset list, so a storage added in PVE's UI is reflected on the next tree load — no cache, no shadow state; the tree reloads after every job (success and failure, the 0.3.3 lesson). *Failure as the user meets it:* the naming guard fires in the dialog before submit, in red on the field, with the sentence "PVE would inventory `vm-100-disk-1` as a guest disk"; daemon refusals name the storage and the dataset ("`local-zfs` owns `rpool/data/vm-100-disk-0`"), never "this pool". *Proof:* Playwright spec over a stunt-node PVE pool (`pvesm add zfspool` — PVE's own tool — with a `vm-100-disk-0` zvol, a `subvol-101-disk-0`, a `basevol-102-disk-0` and an ANAS sibling): badges, disabled/enabled toolbar per node, create-with-note, naming-guard message, reload after success and after an injected failure. Live proof of every daemon refusal path and of the system-pool loop ground truth.

**Whole-image restore onto a LUN and the restore mark (cr3.lunrestore; `services/backup-restore.ts`, `services/restore-mark.ts`).** The rule: no initiator is served an image that is not complete and verified through ANAS's own action. *The mark*: before the first byte is written to a zvol, ANAS sets the ZFS user property `anas:restore` on it (JSON: repository, namespace, snapshot, archive, start time, `state: writing | unverified`, a reason), and removes it (`zfs inherit`) only after the stream exited 0, the client reported the restore complete and the size was read back equal. It is the object's own state, the pattern of the `anas:schedule` stamp (node ground truth, OpenZFS 2.4.2: the property survives a full overwrite, is not reverted by a rollback, does not travel with a plain send). Mark and a running restore job onto that backing = in progress; mark and no running job = interrupted; `unverified` = the client reported the image complete and ANAS could not confirm it; a mark that cannot be read is never treated as absent. All marks of a read come from one command: `zfs get -Hp -o name,value,source anas:restore -- <volumes>` for two or more volumes, `-o value,source` for one (an image file's mark is read with its own `getfattr`, one per file). A restore that finds an earlier restore's mark puts it back exactly if it wrote nothing itself, and refuses before touching anything when the earlier mark cannot be read. *An image file carries the same mark* (cr3.lunrestore.filemark; until then an image file carried none and only the job records below stood in): the extended attribute `trusted.anas.restore` on the file itself, the same JSON, states and lifecycle, read with `getfattr --absolute-names -e hex -n trusted.anas.restore -- <file>` (both tools run with `LC_ALL=C`, since their error lines are matched in English, and with a 10 s budget in every lane, so a hung filesystem reads unknown instead of holding a job and the iSCSI lock; a mark that cannot be read is named with this exact command and when the door opens again), set with `setfattr -n trusted.anas.restore -v 0x<hex> -- <file>` (always hex: setfattr reads a value beginning `0x` or `0s` as an encoding) and removed with `setfattr -x`. `attr` is an installer dependency, probed at `/usr/bin/setfattr` and `/usr/bin/getfattr` (the paths the daemon runs) on every install and upgrade, and marked manually installed so `apt autoremove` keeps it. `trusted.` is root's namespace: a share user who can write the image can neither read, set nor remove the mark. Where the technology differs (ground truth `packages/daemon/src/fixtures/restore-mark/README.md`, OpenZFS 2.4.2, ext4, btrfs): the attribute is on the inode, so the restore's `'w'` open and a `truncate -s` keep it; it travels with the file's data where a volume's property does not: `cp -a`, `rsync -aX` and `mv` (on one filesystem and across filesystems), the `.zfs/snapshot` copy, a plain `zfs send | zfs recv`, a `zfs clone` and a btrfs snapshot carry it, a `zfs rollback` puts back what the snapshot holds (a mark removed after it comes back, a mark set after it goes), and `cp` or `rsync` with no options drops it (each captured, `fixtures/restore-mark/travel.*` and `investigation.*`; not captured: `zfs send -R` or a raw send, `cp --reflink`, a copy over NFS or SMB); and since the open empties the file, a run that wrote nothing after opening it keeps its own mark. A file that is not there reads absent, as a volume that is not there does. *Where a file cannot carry a mark* (no `setfattr`/`getfattr` on the node, as on a node upgraded by hand without the installer; a filesystem that refuses extended attributes, such as vfat; OpenZFS 2.4.2 with `xattr=off` does not refuse, `fixtures/restore-mark/limits.anas-zfs.txt`) the read is `unsupported` with its reason, never absent or unknown, and the daemon's job records stand in. The last restore onto the file that failed with `IMAGE_PARTIAL` or `IMAGE_UNVERIFIED` stands until a later restore onto it completes or a later Enable of its target completes; the queue keeps such a record past its ordinary eviction (up to 100 of them); the record is lost when the daemon restarts, and every sentence that relies on it says so and says why the file has no mark. *When a mark and a record both speak* (`restoreVerdict`, `services/restore-mark.ts`) the mark is the truth and the record adds the job's id; an image file whose mark is absent still answers to a standing record (a restore that ran where no mark could be set), a volume's absent mark does not. *New LUN*: backing → mark → backstore created unmapped → stream → size read back → mark removed → mapped at the lowest free index, granted to the ACLs, saved; a LUN is never mapped before its image is verified, and after the stream may have started nothing is destroyed: an image that cannot be verified is kept unmapped with its mark. A failed run removes only what an identity re-read proves it made (name, plugin, serial, path, mapped by nothing). *In place*: prior mark read → target disabled and saved → mark → stream → verify → mark removed → target enabled again. *"Nothing was written"* is said, and the previous state restored, only when the client never started, or exited non-zero with one of its captured pre-fetch refusals (missing snapshot or archive, permissions, connection refused, DNS, certificate) on a line of its own and no progress line at all; a signal, a broken pipe, a deadline, a failed flush or any unrecognised line keeps the target disabled or the LUN unmapped. Opening an image file for the restore empties it, so a failure after the open leaves a shorter file: the in-place door refuses a file whose size is not the image's, and the sentences name `truncate -s <bytes> <path>` before restoring again. *Doors gated by the mark or the record*: Enable is refused while a restore runs (409 `restore-in-progress`), confirm-gated when the image is partial or unverified (the confirm signs what was shown and removes the mark; the job re-checks under the lock and enables nothing if it changed), and refused when a mark is unreadable; adding an initiator to such a target, adding a marked volume as a LUN, and Repair of a hole whose backing is marked, or whose image file has no mark while a failed restore record onto it stands (reason `restore-mark`), are refused; a file LUN is always added as a new image created with `O_EXCL`, so a marked image file is never adopted as a LUN. *An unmapped backstore* holds its backing like a LUN: pool destroy and export, dataset destroy, rollback and any volsize change, the AHR verbs, mounts and a file restore refuse with the held-by sentence; the dashboard shows it with what the mark says, and adding its device as a second backstore is refused.

**Cross-feature gates (iscsi.6):** every list/detail row of Pools, Datasets, AHR pools and Mounts carries an additive `heldByLun` (`IscsiHeldByLun`: target, index, name, backing path, connected initiators, the one `detail` sentence) answered ONCE per request from `iscsiClaims()` (never per row; absent on an old daemon ⇒ no gating). Refused up front with a guiding 409 (no confirm bypass) while a LUN holds the object: volume rollback / volsize shrink / rename (seam — no endpoint exists yet), dataset destroy (incl. `-r` over a child zvol), snapshot rollback of a dataset holding an image, **ZFS pool destroy and export** (ZFS does not reliably refuse `zpool destroy` over a claimed zvol), AHR destroy / change-mount (AHR has no unmount verb), mount unmount / disable / remove. `busy-diagnosis` gains the LIO branch (`held by iSCSI LUN <n> '<name>' of target <iqn> (<path>)`, `fuser` not consulted); a busy zvol destroy quotes a dataset, which the path extractor now reads. `GET /v1/iscsi/targets/:iqn` carries `firewall` (`IscsiFirewallAdvisory`, read-only from `pve-firewall status` + `/etc/pve/firewall/*.fw`; advisory only on enabled + nothing admits 3260/tcp; never written). Disks: `Disk.handsOff`/`handsOffReason` (`iscsi-served-here` when an iSCSI-transport disk's serial matches a LUN this node serves), `zd*` excluded like loop/zram, and one shared `isComposableDisk()` predicate at every composer/spare/expand candidate site. **Backing tiers:** `IscsiLunKind` = `zvol | file | foreign | unresolved` — `unresolved` = a path that resolves onto no known storage NOW (pool exported, file absent); the ANAS IQN convention is authoritative for ownership `anas`, only a backing that POSITIVELY resolves onto PVE-managed or non-ANAS storage makes a target `foreign`, and a target with no LUNs is ANAS's (a fresh target could otherwise never receive its first LUN). **Boot ordering** ships as a drop-in `/etc/systemd/system/rtslib-fb-targetctl.service.d/anas-ordering.conf` (`Wants=`/`After=zfs-volumes.target zfs-volume-wait.service`, `After=zfs-mount.service zfs-import.target local-fs.target`; `Wants=` not `Requires=` so LIO still starts without ZFS; `After=` also orders the stop, so the target goes down before pools export). Honest limit: AHR pools mount from fstab with `nofail`, which drops the mount unit's `Before=local-fs.target`, and mount units are per-pool — no static `After=` can name them; the correct mechanism is `x-systemd.before=rtslib-fb-targetctl.service` on the AHR fstab line (a migration for existing pools — candidate, not built). `targetcli-fb` + `python3-rtslib-fb` are hard dependencies installed by `install.sh` (`--install-deps`); the rtslib postinst enables and starts `rtslib-fb-targetctl` itself; `uninstall.sh` removes only the drop-in — never the packages, `saveconfig.json`, or the live tree. `DashboardWarning.category` gains `iscsi`. **Stubs (live-proof F2, `iscsi.8`):** `targetctl restore` CREATES a missing fileio backing file at the persisted size when the mountpoint directory exists — a late or failed mount therefore yields an ACTIVATED LUN serving zeros with the right serial, not a hole. Health detects a stub (size 0 against the persisted size, or the containing mount is not the file's dataset/AHR pool) as `stubLuns[]`; a zero-size stub on an ANAS-owned target sets `degraded` and ANAS quarantines it (unmap that LUN, delete the stub backstore and 0-byte file, keep the persisted record, never `saveconfig`) so it becomes an honest `missingLuns` hole for Repair; a full-size image whose only signal is the containing mount is reported, does not degrade the node and is left serving, since it holds data; AHR fstab lines that carry a LUN get `x-systemd.before=rtslib-fb-targetctl.service`. A wildcard portal (`0.0.0.0` / `::`) is refused at the schema with a guiding message (threat model; GT-8) — relax deliberately if ever wanted. Key decisions: **serial + attributes are replayed on every backstore recreate** (boot restore, fileio resize, image restore) — initiators, ESXi, Windows and PVE's own volids identify a LUN by the serial, and LIO drops attributes on recreate. Backstores reference `/dev/zvol/<pool>/<vol>` (the `zd*` name changes across reboots). **Boot restore reports systemd success even when a LUN is missing**, so `/v1/iscsi/health` diffs rather than trusting the unit, and ANAS never runs `saveconfig` over a degraded restore. LIO's own 10 rotating `saveconfig` copies are the config backup; every mutation is a journald audit line. `rtslib-fb-targetctl` is ordered after `zfs-volumes.target` and AHR activation via a drop-in. Cross-feature gates (Pools/Datasets/AHR/Mounts): destroy/export of a claimed zvol already fails in ZFS (`busy-diagnosis` names the LUN from configfs — `fuser`/`lsof` see nothing); **rollback, rename, volsize shrink and removal of a backing file succeed silently in ZFS and are refused by ANAS** while a LUN references the object. The disk inventory excludes `zd*` and tags iSCSI-transport disks whose serial matches a LUN served by this node.
