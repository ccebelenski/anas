# Cloud sync

## Cloud sync — rclone (rclone.1–3; designed 2026-09-23, GitHub #57)

One-way `copy` or `sync` of a local path (a dataset mountpoint, a share path, any directory) to an rclone remote, on the schedule-unit pattern, with a job and a notification per run. rclone is used as it is: every backend it supports works, there is no cloud-vendor code in ANAS, and copying data back is the operator's own `rclone copy` on the node. Not built: two-way sync, a restore UI, retention or versioning on the remote (`--backup-dir`).

**Ground truth 2026-09-23 (stunt node, PVE 9.2.20 / Debian 13.7):** Debian trixie ships **rclone 1.60.1** (2022) as `rclone`, a Go binary with no dependencies, and that is the version ANAS is built against — a newer upstream `.deb` replaces the same `/usr/bin/rclone` and every interface used here predates 1.60 (`config providers`, `config dump`, `obscure -`, `lsjson`, `about --json`, `sync`/`copy` with `--use-json-log`). Facts that shaped the design: `rclone rc --loopback` gives every config verb as JSON, but the input can only arrive as an argv string (`--json -` and a piped stdin both fail), so a secret written through rclone's own verbs would ride argv — which the iSCSI ruling forbids; `rclone obscure -` reads the password from stdin; rclone's own rewrite of `rclone.conf` preserves comments and unusual values verbatim (`# anas:…` survived a `config/update`); `config/paths` does not exist in 1.60 (the human `rclone config paths` names `/root/.config/rclone/rclone.conf` for root); the anasd unit runs with **no `HOME`** in its environment, so rclone's default config resolution is undefined under the daemon and the path must be passed explicitly; passwords land in the file obscured (reversible, rclone's own model), while an S3 `secret_access_key` is stored plain because rclone 1.60 does not type it as a password; a `drive` remote created `nonInteractive` answers with a `State` question (`config_is_local`) instead of a remote — OAuth backends need a token from a browser machine; exit codes: `0` ok, `3` source or destination directory missing, `7` fatal (`--max-delete` reached), **`1` for every `NewFs` failure — unreachable, authentication and unknown-remote all exit 1**, so a verdict comes from the message, not the code; `--use-json-log` emits one object per event and a `stats` object at every `--stats` interval with `bytes`, `totalBytes`, `transfers`, `checks`, `deletes`, `errors`, `eta`, `speed`, `fatalError`; a `sync` from an empty source deletes the whole destination (dry run showed 4 files + 1 directory), which is the failure to guard.

**Remotes = ANAS's own `rclone.conf`.** ANAS keeps its remotes in **`/etc/anas/rclone.conf`** (mode 0600 root, beside the mount credentials; created when absent), passed on every invocation as `--config /etc/anas/rclone.conf --ask-password=false`. Root's own `~/.config/rclone/rclone.conf` is never read or written — **ruled 2026-09-23 (operator): a file root edits independently is not a store ANAS controls**; the operator's rclone habits stay theirs and ANAS's remotes are ANAS's. Per node, never pmxcfs (secrets, like mount credentials). A copy-back on the node therefore names the file: `rclone --config /etc/anas/rclone.conf copy <remote>:<path> <directory>`. A password-protected configuration is reported as a fact on the Remotes screen and refuses every mutation (`409 config-encrypted`) — ANAS neither prompts nor stores the passphrase. **Reads** go through `rclone config dump` (JSON): a remote is `{name, type, options: {non-secret key → value}, secretsSet: [keys]}` — a secret value is never returned. A non-secret value is shown only in a shape that cannot carry a secret (`classifyOptionValue`, the one classifier for every answer, job result and confirm): a plain value as it is; a URL with a userinfo, query or fragment part with those parts shown as `[secret]`; anything else (a value with an inline `,<key>=` setting or starting with `:`, a reference option that is not plain `<name>:<path>` entries or absolute paths, a value with `://` that is not one strict URL) hidden whole as `[hidden: this value carries inline settings]`. A key is a secret when the provider schema flags it `IsPassword`, when its name ends in `pass`, `password`, `secret`, `token` or `key` (b2 `key`, s3 `secret_access_key`, `client_secret`, `token`, `sse_customer_key`; `access_key_id` and `key_file` are not), or when it is one of the named credential options the suffix misses (`SECRET_NAMES`: `sas_url`, `key_pem`, `service_account_credentials`, `authorization`, `sse_customer_key_base64`, `sse_customer_key_md5`, `headers`, `set_env`) — and never when the option is a `bool` (`sftp.ask_password` matches the suffix but is a switch, not a credential) — rclone 1.60 has no `Sensitive` flag, so this generic name rule stands in for it. **Writes are ANAS's own surgical INI edit** of the section (add / replace / remove; every other byte of the file untouched, comments included), write-temp-then-rename 0600 under the per-file lock, then a gate — `rclone config dump` must parse the file and list the section — with a byte-identical rollback when it does not (the `testparm` pattern). Password-typed values are obscured through `rclone obscure -` on stdin; **no secret ever enters an argv** (the `iscsi-mutate.ts` argv guard is reused as the executor-side backstop). Type is immutable after creation (rclone's own posture; a retype is a new remote). Delete is a hard `409` while a task or another remote references the remote, and while another remote's reference option is hidden, so whether it references this one cannot be told. **Test** (`POST /v1/cloud/remotes/test`) is the mounts / repo-Test shape: `timeout`-bounded `rclone lsjson <remote>:<path> --max-depth 1 --contimeout 10s --timeout 30s --retries 1 --low-level-retries 1` → `ok` / `unreachable` (`i/o timeout`, `connection refused`, `no such host`) / `auth` (`unable to authenticate`, `handshake failed`, `401`, `403`, `AccessDenied`, `InvalidAccessKeyId`, `SignatureDoesNotMatch`) / `not-found` (exit 3) / `error` with rclone's last line verbatim — the classifier is a heuristic over backend-specific text and `error` is the honest fallback. Testing an UNSAVED dialog needs `Sys.Modify` (the options typed can act on the node): without it the request is refused `403` at the route, and the job queue and the cancel door hold its job (`cloud.remote.test`) to `Sys.Modify` as well; `Sys.Audit` tests saved remotes by name. A Test of an UNSAVED dialog is served through an environment-defined remote (`RCLONE_CONFIG_ANASTEST_<KEY>`, obscured where the file would be) so nothing is written before the user saves — **GT 2026-09-23 on 1.60.1: works, and the password MUST be obscured on the environment too** (rclone reveals every `IsPassword` field wherever it reads it; a plain value fails with "input too short when revealing password"). **GT 2026-09-24: rclone WRITES its config file on its own** — the sftp backend persists `shell_type`, `md5sum_command`, `sha1sum_command` on first connect (appended to a saved remote's section; a NEW `[anastest]` section for an env-defined one, and it creates the file when absent); other sections and comments survive. Rule: an unsaved-dialog probe runs against a private 0600 temp COPY of the file (`/run/anas/rclone-probe-*/`, removed in a `finally`) so nothing of the dialog ever lands in ANAS's file; a saved-remote probe or run uses the real file and rclone's appended keys are ordinary foreign keys — kept by the INI writer, listed under `options`, never a defect. **Providers** (`GET /v1/cloud/providers`) is `rclone config providers` (396 KB, 46 backends) trimmed per option to `name, help, type, required, secret, default, examples[], provider (the `Provider` filter, `AWS,Alibaba` or `!AWS`), advanced` — the metadata the dialog renders from; read per request, not cached.

**Tasks = systemd units, `anas-cloud-<name>.service` / `.timer`,** the fifth unit store on the ONE helper module (`systemd-unit-store.ts`; `X-ANAS-Task=` marker, `Persistent=true`, never adopt a unit without the marker). `CloudSyncTask = { name, source (absolute path), remote (name), path (remote-side, may be empty), mode: copy | sync (default copy), excludes[], bwlimit? (rclone syntax, e.g. `8M`), notify (default always — the task is the operator's offsite copy, backup parity), schedule, cadence?, enabled }`. `cadence` reuses the backup cadence schema and generator (renamed `TaskCadence` with `BackupCadence` kept as an alias; biweekly parity gate, `SuccessExitStatus=75` skip, cadence-aware overdue — all as backup). The runner `dist/cloud-task.js` is the backup runner's twin (POST `…/run` with `direct:true`, poll, exit truthfully); Run Now starts the unit and supervises it, so scheduled and manual runs share one history. **Extraction, not a copy:** status derivation, journald reads, the parity gate and unit supervision in `backup-units.ts` are generic in everything but the unit prefix — they move to a prefix-parameterised shared module that backup and cloud both import, with backup's tests kept green. **The run job:** (1) source guard — the path must exist, and a path on a configured-but-unmounted mount is refused with the mount named (this is the backup2.11 guard; it is built here as ONE shared helper and backup2.11 wires it into backup); (2) `sync` with an EMPTY source directory is refused: "an empty source in sync mode would delete everything at the destination" — the catastrophic shape, guarded up front; `copy` never deletes and has no such guard. Implications, stated in the dialog: a `copy` task accumulates at the destination — a file deleted or renamed on the source stays (or exists twice) at the remote until the operator cleans up; a `sync` task mirrors the source exactly, deletions included; a source the user emptied ON PURPOSE is refused in sync mode until the remote is emptied by hand (`rclone --config … purge`), the price of the guard; a half-missing source is not a guard case — sync does what it says. A guard fires at a scheduled run as well as at Run now: the run FAILS with the sentence, notifies and shows on the dashboard — never a silent skip. Only fstab-configured mounts are detectable as unmounted; an absent path is refused by the existence check, and an empty mountpoint directory in copy mode is a harmless no-op; (3) consistency is derived per source exactly as backup derives it (ZFS dataset or a directory in one, AHR pool with the `@data`/`@snapshots` layout → a transient snapshot `anas-cloud-<task>-<unix>` through the shared snapshot helper, destroyed in a `finally`, swept at run start; remote mounts, foreign filesystems, flat AHR → live, labeled); the rclone source becomes the snapshot path; in snapshot mode the nested filesystems under the source are not included (a snapshot holds one filesystem), and the run excludes each one with an anchored `--exclude /<path>/**` rule, so their copies at the destination are left as they are; the set comes from complete reads (every mount under the source in the mount table, plus `zfs list -H -o name,mountpoint,canmount -t filesystem` for a ZFS source or `btrfs subvolume list` for an AHR one), and a snapshot-mode `sync` is refused when those reads fail or a nested name carries a control character; a live copy reads through the nested filesystems and includes them — the dialog says which before save, from the existing `preview-nested` scan; (4) `rclone <mode> <src> <remote>:<path> --config … --ask-password=false --use-json-log -v --stats 5s --stats-log-level NOTICE [--bwlimit] [--exclude …]` under the daemon's executor (`execFile`, no shell); each `stats` object updates the job's progress (bytes / total, files, checks, deletes, errors, ETA); the final `stats` object is the result; `-v` adds one JSON event per finished file and per error, and together with the 5 s stats cadence (was 30 s) feeds the job's live `detail` — the run viewer's data (rclone.6), in-memory on the job, gone when the job leaves the queue. **Exit-code policy:** `0` and `9` (nothing to transfer) complete; everything else — including `6`, "less serious errors", which means files are missing at the destination — fails, with rclone's error lines in the job and the notification. `--max-delete` is not set: the empty-source guard covers the catastrophe and a partial ceiling is a policy knob with no honest default. Notifications through `pve-notify.ts` with `anas-cloud-{subject,body}.txt.hbs` (`type=anas-cloud`): task, `source → remote:path`, mode, live/snapshot label, transferred bytes and files, checks, deletes, errors, duration, the error lines on failure; skips never notify; delivery never fails the run. Dashboard warning category `cloud`: failures and silently-overdue, pull only.

**Workflow (equal weight — §2 rule).** *Where it lives:* one new menu, **Cloud Sync**, after Backup, built as Backup is: the Tasks grid with the toolbar (Create, Edit, Remove, Run now, Preview, Enable/Disable, Remotes…) and the **Remotes** manager window behind the Remotes… button — the Repositories manager's twin. Nothing in the Backup menu changes. *Remotes, happy path:* Remotes… → the grid lists every remote in the file (name, type, `set` keys) with the file path and rclone's version in the footer → Add → Name, Type (46 entries, description shown) → the fields render from the provider schema, guided for the curated backends (rclone.4): one sentence naming where the essential values come from, the essential fields first — filtered by the chosen `provider` where the backend has one (S3's `region` and `endpoint` rows appear once, for the provider picked) — then the optional own-OAuth-client fields under a collapsed "Use your own OAuth client" row (rclone's built-in client is shared and rate-limited) and every other non-advanced option under a collapsed "More options", with the "Show advanced options" toggle for the rest; a backend with a `token` option shows the one sentence *"This backend authorises through a browser. On a machine with one, run `rclone authorize "<type>"` and paste its output into the token field."* — every option of the backend still renders somewhere, and a backend outside the curation renders as it always did → Test (verdict sentence in the dialog) → Save → job → the grid reloads on success and on failure. Edit shows non-secret values as the classifier shows them; a secret field is blank and reads "(unchanged)"; typing replaces it, and each stored secret has a "Remove the stored value" box that sends `null` for it. Remove of a referenced remote is refused with the task names. The window footer carries the copy-back sentence: *"To copy data back, run on this node: `rclone --config /etc/anas/rclone.conf copy <remote>:<path> <directory>`."* *Tasks, happy path:* Create → Name → Source (the `ANAS.pathPicker`, live backend; PVE-owned paths refused as everywhere) → the consistency line ("backed up from a snapshot" / "live copy — <reason>") and, when the scan finds them, *"Contains N nested filesystems that will not be included: <paths> (a snapshot holds one filesystem; their copies at the destination are left as they are)"* for a snapshot-mode source, *"Contains N nested filesystems that will be included: <paths> (a live copy reads through them)"* for a live one → Remote (combo of saved remotes; empty ⇒ the guiding "Add a remote first (Remotes…)" toast, the backup precedent) + Path on the remote → Mode: `Copy` (default) / `Sync` with the one sentence under it: *"Sync deletes files at the destination that are no longer in the source. Copy never deletes."* → **Preview** (the dry run: "would transfer N files / M bytes, delete K files at the destination" and the first deletes listed; on `sync` a preview that would delete everything says so in red; the same **Preview** on the toolbar dry-runs the SAVED task in the display-only `anas-win-cloud-preview` window) → Excludes → Bandwidth limit (optional) → Schedule (the backup cadence widget, reused) → Notify → Save → job → the grid reloads on success and on failure with the new row selected. Run now → the job appears on the dashboard strip with rclone's progress (bytes of total, files, ETA); the row's Last run refreshes when the job ends, success or failure. Detail window: config, consistency, `source → remote:path`, the unit and timer as written, recent runs from journald (labeled recent-only; "history is not retained while disabled"). *Timeliness:* the grid derives everything from unit + timer state per load (no shadow state); it reloads after every job of its own, success AND failure; a run started by the timer shows on the next load or the dashboard pull — a stale Last run after a job the user did not start is not a defect, a stale one after a job they did is. *Failure as the user meets it:* refusals are `400`/`409` sentences that name the thing — the unmounted mount, the empty source in sync mode, the encrypted configuration, the remote's referencing tasks — shown in the dialog with the field or in the toast, never a bare "failed"; a failed run is a red Last run cell whose tooltip is rclone's last error line, the same line the notification carries, and the recovery verb (Run now, Edit, Remotes…) is on the same toolbar. *Watching a run (rclone.6):* the running job publishes a live `CloudRunDetail` on itself (in-memory, gone when the job leaves the queue — no shadow state), and the Tasks toolbar's **View run** opens a dashboard window over it — progress bars, a throughput spark from the last 5 minutes of samples, per-file figures, the in-flight transfers, the recent events, the stalled label; the same small spark rides the dashboard's jobs strip and a tiny one the task row, and Cancel run is in the window. Per-file detail is shown only while a run is in progress; a finished run's facts stay in the journal and the recent-runs list. *Proof:* the stunt node's own `sshd` is the real remote (`sftp` to `127.0.0.1`, password auth) — Playwright over the Remotes window (add with password → the file holds an obscured value and the API never returns it; Test `ok`, `auth` with a wrong password, `unreachable` against 192.0.2.1, `not-found`; edit keeps the secret; remove refused while referenced) and over the Tasks grid (create with the nested note, copy run → files present on the remote path, sync run → a deleted source file disappears at the destination, empty-source sync refused, unmounted-mount source refused, a failed run's cell + notification, reload after an injected failure); the run's `journalctl` shows the JSON stats and the unit's own result.

**Simplicity check (operator rule, 2026-09-22).** No picker for the config path (one file, ANAS's own). No second store — the INI writer exists only because rclone's verbs would put secrets on argv; the file stays rclone's and rclone reads it back as the gate. The provider-schema form is the one piece of mechanism, and it is what keeps "any backend rclone supports" true without vendor code; a curated subset would BE vendor code. No `--max-delete`, no retention, no two-way, no rate schedule. (A dry-run preview was cut here and reinstated 2026-09-24 by the operator: once sync's only protection is the empty-source guard, letting the user see the deletes before they save is the cheapest safety there is.) OAuth is rclone's documented headless flow, not an ANAS browser dance. The secret name rule is a heuristic and is stated as one.

**Honest limits.** rclone 1.60.1 is a 2022 release; backends added or changed since (new S3 providers, Proton, etc.) are absent until the operator installs a newer rclone, which ANAS uses unchanged. **No supported newer path exists (checked 2026-09-23):** Debian has no `trixie-backports` rclone (only sid carries 1.69.3), and upstream ships a bare `.deb` with no signed apt repository — so a newer rclone is the operator's manual install and manual updates, never something `install.sh` does. Obscured is not encrypted — the file's protection is its 0600 mode, rclone's own posture. A token refresh rclone writes into the file during a run can lose to a simultaneous remote edit in ANAS (whole-file rewrite vs. surgical edit); the next run refreshes again from the same refresh token, so nothing is lost but one write. The Test verdict classifier reads backend text; an unrecognised failure is `error` with the text, never a wrong bucket.
