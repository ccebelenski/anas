# Replication

## Replication — zfs send over ssh

Push replication of ZFS datasets with `zfs send | zfs recv`. The source is always a dataset on this node; the receive runs on this node, on a cluster peer, or on a registered remote over ssh. Nothing about a replication is stored outside ZFS and the task units: the incremental base is found in ZFS on every run, and the newest snapshot both sides share is the record of the last replication. Code (daemon paths under `packages/daemon/src/`): the run is `routes/replication.ts`; target guards `services/replication-target.ts`; ssh `services/replication-transport.ts`; holds `services/replication-holds.ts`; remotes and keys `routes/replication-remotes.ts` + `services/replication-remotes.ts`; recurring tasks `routes/replication-tasks.ts` + `services/replication-units.ts` + the runner `replicate-task.ts`; recursive runs `services/replication-tree.ts` (planner), `services/replication-tree-read.ts` (reads), `services/replication-tree-gate.ts` (gates), `parsers/zfs-tree.ts`; schemas `packages/shared/src/schemas/replication.ts`; the panel `packages/pve-integration/src/65-replication.js`. The task and remote routes are listed in the route index below; the two dataset-scoped routes are dispatched from the datasets wildcard (`routes/datasets.ts`):

| Method | Path | Description | Response |
|--------|------|-------------|----------|
| `POST` | `/v1/pools/:name/datasets/*path/replicate/plan` | Dry run (`planReplication`): `{target, snapshot?}` → `{mode, snapshot, baseSnapshot?, estimatedBytes, targetExists, targetDiverged, upToDate?}`. Reads only; a diverged target is reported with a full-send estimate; a target that already has the snapshot answers `upToDate: true` with `estimatedBytes: 0`; a target the base rule (step 5) refuses answers `409` with the rule's sentence; a snapshot listing that failed answers `503` | `200` |
| `POST` | `/v1/pools/:name/datasets/*path/replicate` | Run (`runReplication`): `ReplicateRequest` = `{target, snapshot?, snapshotFirst?, notify?, recursive?, exclude?}`. An empty `*path` (`…/datasets/replicate`) is the pool-root dataset | `202` with job |

**Targets.** `ReplicationTarget = {pool, dataset?, location?}`, `location = {kind: local | peer | remote, name?}`, absent = local (`resolveTargetPlacement`, `resolveLocation`):

| Placement | How it is resolved | How it is reached |
|-----------|--------------------|-------------------|
| local | this node; the target pool must be in this node's `zpool list` | a second local `/usr/sbin/zfs` process |
| peer | `name` must be a node in `/etc/pve/.members` and must not be this node (`'<name>' is THIS node — use a local target, not a peer`, `peer '<name>' is not a known cluster node`) | `ssh … -- root@<node>` over the root ssh trust PVE keeps between cluster nodes: no ANAS key, the system `known_hosts` |
| remote | `name` must be in the registry `/etc/pve/anas/remotes.json` (pmxcfs, cluster-wide) as `{name, host, port (default 22), user (default root), hostKeyFingerprint?}` (`remote '<name>' is not registered`) | `ssh … -p <port> -i /etc/pve/priv/anas/replication_key -o UserKnownHostsFile=/etc/pve/priv/anas/known_hosts -o StrictHostKeyChecking=yes -- <user>@<host>` |

The target dataset is `<target pool>/<target.dataset>` when `dataset` is given; otherwise the source's own pool-relative path, and for a pool-root source the source pool's name (`tank` → `backup/tank`); an empty `dataset` is the same as an absent one (`resolveTarget`, `resolveTaskDatasets`). The far side needs sshd and ZFS; nothing is installed there, and remote commands call `zfs` and `zpool` unqualified, so the remote user's login `PATH` must find them (`ZFS_REMOTE`). A TrueNAS host or a plain Linux host with ZFS works as a remote. Every ssh carries `-o BatchMode=yes -o ConnectTimeout=10 -o ServerAliveInterval=15 -o ServerAliveCountMax=4` and `--` before the destination (`buildSshArgv`, `SSH_LIVENESS_OPTIONS`).

**The cluster key and pinned host keys.** One ed25519 keypair serves the whole cluster: `/etc/pve/priv/anas/replication_key`, created by `POST /v1/replication/remotes/keypair` as `ssh-keygen -t ed25519 -N '' -C anas-replication -f <path>` and never regenerated while its `.pub` exists (`ensureKeypair`); `GET /v1/replication/remotes` returns the public key for the remote's `authorized_keys` (`''` when there is none) beside the registry. Registry writes are compare-and-swap on the file's `version` (a moved version answers `409`). Remote host keys are pinned in ANAS's own `/etc/pve/priv/anas/known_hosts`. The test probe (`POST /v1/replication/remotes/test` for typed values, `…/remotes/:name/test` for a registered one; `diagnose`) reports one stage: `unreachable`, `hostkey-unknown` (with the fingerprint `ssh-keyscan -T 10` saw, ed25519 preferred), `hostkey-changed` (pinned and presented fingerprints both), `auth-failed`, `no-zfs` (`ssh … zfs --version` failed) or `ok` with the remote's ZFS version. A pin (`?pin=true`) or re-trust (`?retrust=true`) must carry the fingerprint the operator was shown and runs as a job that scans again and writes only when the host still presents that key, else `409 STATE_CHANGED` and `known_hosts` is left as it was; an ordinary pin never replaces a pinned key, and a re-trust replaces only the lines for that host and port (`pinHostKey`). A remote named by a replication task on this node cannot be deleted (`Remote '<name>' is still used by replication task(s): <tasks> — remove them first`); when this node's task units cannot all be read the delete is refused `503` (`Could not read every replication task on this node, so whether one still uses remote '<name>' is not known — refusing; remove or repair the task that cannot be read, then delete the remote`). Tasks on other cluster nodes are not read, and a completed delete carries the note `Only this node's replication tasks were checked; a task on another cluster node that used remote '<name>' fails at its next run until it is edited or removed`.

**One run of one dataset** (`runReplication`; a request without `recursive: true`):

1. *At the request.* The body must parse as `ReplicateRequest` (`400 Invalid replicate request: <issue>`); the caller's identity is required; a named snapshot that is a backup or cloud transient is refused (`400`, `'<source>@<snapshot>': snapshot names beginning with 'anas-backup-' or 'anas-cloud-' are reserved for backup and cloud runs and are never replicated by name — name another snapshot, or none for the newest`); the source must exist (`404 Dataset '<source>' not found`). With `snapshotFirst`, a PVE-owned source is refused (`409 PVE_MANAGED`, `Snapshot-first replication would snapshot '<source>' — <reason>`); without it, the source's ownership is not checked. Then the target guard (`guardReplicationTarget`, `400` with its sentence): the location resolves; the target pool exists where the target lives (`Target pool '<pool>' does not exist`, with ` on <kind> '<name>'` for a peer or remote, and with `: ZFS is not available on this node: <reason>` on a local node without the `zpool` command or the zfs module); a pool listing that did not answer is refused as unreadable, never as a missing pool (`Could not list the pools on this node: <line>` for a local target, `Could not list the pools on <kind> '<name>': <line>` for a peer or remote, the line being ssh's own last line of stderr for an ssh failure and the command's first line otherwise); for a local target only, the target dataset is not PVE-owned (`Replication target '<target>' is PVE-owned — <reason>`), its name would not be inventoried by a PVE storage as a guest disk (`pveNamingGuardMessage`), and it is not the source (`Cannot replicate '<source>' onto itself — choose a different target dataset`).
2. *Claims and lane.* A shared claim on the source dataset (a destroy, rename or rollback of it waits for the send); for a local target an exclusive claim on the target dataset (`datasetSourceClaims`, `zfsDatasetClaims`). The job runs in the `long` lane, which data movers may fill to at most three of the queue's four slots (`jobs/queue.ts`); the pipeline has no deadline.
3. *In the job.* The target guard runs again on a freshly loaded PVE footprint and a refusal fails the job as `409 STATE_CHANGED` with the guard's sentence. With `snapshotFirst`, the source's ownership is judged again (`Snapshot-first replication refused: '<source>' is PVE-owned — <reason>`) and `zfs snapshot -- <source>@snapshot-<UTC ISO time with : and . replaced by ->` is taken through the shared `createZfsSnapshot`.
4. *The snapshot sent (S).* The request's `snapshot` (it must exist: `Snapshot '<source>@<snapshot>' does not exist on source`), else the snapshot-first one, else the source's newest snapshot that is not a backup or cloud transient (`anas-backup-*`, `anas-cloud-*`, `isTransientRunSnapshot` in `services/snapshot-naming.ts`; `newestReplicable`). Snapshots are ordered newest first by `createtxg`, the order ZFS took them in, never by the clock. A source without such a snapshot fails: `Dataset '<source>' has no snapshots — create a snapshot first`. A source listing that fails stops the run with `Could not list the snapshots of '<source>': <error> — refusing the replication` (the plan answers `503`); it is never read as "no snapshots".
5. *The base* (`discover`, which asks `decideBase` in `services/replication-tree.ts`, the one rule the recursive planner also asks). The target's snapshots are listed newest first in the target's own `createtxg` order (locally with `zfs list -j`; on a peer or remote with `zfs list -H -o name -- <target>` for existence, then `zfs list -H -t snapshot -o name,creation -s createtxg -- <target>` over ssh). A listing that fails, or a remote answer with lines and no row of the target, refuses the run with `Could not list the snapshots of target '<target>'[ on <kind> '<name>']: <error> — refusing the replication; nothing was sent` (the plan answers `503`); it is never read as an empty target. No target dataset → a full send. Otherwise, in order: the target already has S → **up to date**, nothing is sent; the target's newest snapshot is a backup or cloud transient the source still has and it is older than S → that transient is the base for this one send, and the hold settle then moves the chain's hold to S; the same transient newer than S → refused (`Target '<target>' already has '@<T>' (a backup or cloud run's snapshot), which is newer than '@<S>' — replicate a newer snapshot`); a non-transient snapshot both sides have that is newer than S → refused (`Target '<target>' already has '@<newer>', which is newer than '@<S>' — replicate '@<newer>' or a later snapshot`); otherwise the base is the newest non-transient source snapshot older than S that the target also has. When the two sides share snapshots and none of them is a base, the run refuses with a sentence that names them, says the target has not diverged, and names the remedy: roll the target back to the newest common one with `zfs rollback -r <target>@<common>`, or replicate to a new path. Only a target with no snapshot in common is **diverged**: the run fails with `Target '<target>' has diverged — no common snapshot; remove the target dataset or replicate to a new path` and nothing is sent. No forced receive exists. An up-to-date run completes with `bytesEstimated: 0` and `upToDate: [<source>]`: when S is the newest snapshot both sides share, its holds are settled as after a send; when the target's newest snapshot is a transient newer than S that the source still has, the holds are left as they are and a `note` says the next new snapshot is sent from it; when the target already has a newer common snapshot, no hold is moved and a `note` says so.
6. *The estimate.* `zfs send -nvP [-i @<base>] -- <source>@<S>`, always local; its byte count is `bytesEstimated` in the result (`parseSendDryRun`).
7. *The stream.* One `executor.pipeline` of the two commands in the table below. Every receive, full or incremental, passes `-o readonly=on`: a replication task keeps its target read-only, and a target someone made writable is read-only again after the next receive (operator ruling 2026-11-15: the way to use the copy as a live dataset is to remove the task). A non-zero exit on either side fails the job with `Replication failed — recv: <recv stderr>` (or `send: <send stderr>` when the receive printed nothing, or `send exited <n>, recv exited <m>`), the stderr made one line without control characters (`pipelineFailureDetail`). When the receive says the target `has been modified since most recent snapshot`, a hint is added after ZFS's own text (`modifiedTargetHint`): the target was written to after the base, the target's snapshots newer than the base by name, to release any hold on them, and to roll the target back to the base with `zfs rollback -r <target>@<base>`.

| Side | Full send | Incremental send |
|------|-----------|------------------|
| send (always local) | `/usr/sbin/zfs send -- <source>@<S>` | `/usr/sbin/zfs send -i @<base> -- <source>@<S>` |
| receive, local target | `/usr/sbin/zfs recv -o readonly=on -- <target>` | `/usr/sbin/zfs recv -o readonly=on -- <target>` |
| receive, peer or remote | the ssh argv of the placement table, then `zfs recv -o readonly=on -- <target>` | the ssh argv, then `zfs recv -o readonly=on -- <target>` |

8. *Holds* are settled under the chain's tag (below). A hold or release that fails is a warning on the completed job. The target's snapshots are listed again after the receive; a listing that fails keeps the chain's older holds on the target, with the warning `Could not list the snapshots of target '<target>'[ on <kind> '<name>'] after the receive: <error> — the chain's older holds on the target were kept`.
9. *Result and notification.* `{mode, snapshot, baseSnapshot?, bytesEstimated, target, holdTag, warnings?}`; the run notification is sent from the job on success and on failure (below).

**Holds** (`services/replication-holds.ts`). The tag is per chain, a chain being the pair (where, target dataset): `anas-repl-` followed by the first 12 hex digits of `sha256("<location>\n<target dataset>")`, the location being `local` or `<kind>:<name>` (`replicationHoldTag`). It is derived again on every run and recorded nowhere. A task and a one-off replicate into the same target share a tag; two targets of one source have two tags and never release each other's holds. After the receive, `settleReplicationHolds`:

1. holds the new base on both sides: `zfs hold -- <tag> <source>@<S>` locally, and `zfs hold -- <tag> <target>@<S>` locally or over ssh;
2. on each side where that hold succeeded (or the tag was already there), releases the same tag from every other snapshot of that dataset (`zfs release -- <tag> <snapshot>`);
3. on a side where it failed, releases nothing — the previous base stays pinned — and adds two warnings: `Could not place <tag> hold on <snapshot>: <stderr>` and `Kept every hold on <dataset>: its new base is not held, so the previous base stays pinned`;
4. migrates the suffix-less tag `anas-repl` that earlier installs placed for every chain: on a held target side it is released wherever it sits (the target dataset belongs to this chain); on the source it is released only from S and the base, and only when every other task replicating the same source has placed its own tag somewhere on the source, read from the task units (`legacyReleasableOnSource`); a task store that cannot be read in full keeps it, with the warning `Kept the legacy anas-repl hold on <source>: the replication task list could not be read in full, so another task may still rely on it`.

A recursive dataset destroy and a forced rollback whose sweep includes a held snapshot are refused before anything runs, because ZFS stops at a held snapshot only after destroying the unheld ones (`destroyHoldGate`, `rollbackHoldGate` in `routes/datasets.ts`). The holds are read with one `zfs holds -H` over the swept snapshots; holds that cannot be read refuse (`snapshot-holds-unreadable`). The refusal (`snapshot-held`) names each held snapshot and its holder (`describeHolds`): `held by replication task '<task>': <tag>` when a task on this node derives that tag, `held by a replication no task names (an interactive replicate, or a removed task): <tag>`, `held by replication (the shared tag from before per-chain tags): anas-repl`, or `held by '<tag>'` for a tag that is not replication's. Removing a task removes its units only; its data, snapshots and holds stay.

**Remote commands** (`buildSshArgv`, `remoteShellWord`). ssh does not hand an argv to the far side: it joins the words after the destination with single spaces and the remote login shell splits that one string again. Each word of a remote command is therefore passed through `remoteShellWord`: a word made only of ASCII letters, digits and `_ @ % + = : , . / -` is passed unchanged, and every other word, the empty string included, is wrapped in single quotes with an embedded `'` written as `'\''`. ZFS accepts a space in a snapshot name; unquoted, a hold of `tank/data@nightly 2` would reach the remote shell as a hold of `tank/data@nightly` plus a stray word `2`. In csh and tcsh a single-quoted `!` or newline is not literal; ZFS refuses both characters in a name. A failed `zfs hold` counts as "already held" only when its exit status is not 255 (ssh's own failure) and a stderr line reads `cannot hold snapshot '<snapshot>': tag already exists` naming exactly the snapshot that was asked for (`alreadyHeld`); any other failure is a failed hold, with the consequences in step 3 above.

**Guards on a replica** (repl.guard; `readReplicaTarget` in `services/replication-holds.ts`, the doors in `routes/datasets.ts`). Three edits in the Datasets view can cut a replication chain, and each is caught at its door. *Read-only off on a target*: a `PUT` that sets `readonly=false` on a dataset that is read-only now and has a snapshot carrying a replication hold is confirm-gated (409 + `X-Anas-Confirm-Code`, never refused: a failover needs this edit), signing the dataset and every property in the request. The headline is `'<dataset>' is a replication target. While it is read-only nothing changes it.` when the hold is one this node derives for a chain into the dataset (local, or sent from a peer; a child of a recursive target by its root's tag), and `'<dataset>' looks like a replication target: it is read-only and replication holds one of its snapshots. While it is read-only nothing changes it.` when no task on this node derives the hold (a registered remote's chain, the legacy tag, or a read-only source of a one-shot replicate). The warnings say that a write, or a read with access-time updates on, then changes it; that replication into it stops until a rollback; that the next run that sends sets it read-only again; and that keeping the copy live means removing the task on the sending node. Cost: one `zfs get`, one `zfs list` of the dataset's snapshots with hold counts, and at most one `zfs holds` over the newest 64 held snapshots; an edit that does not set `readonly=false` runs none of them, and a predicate read that fails neither blocks nor confirms (logged). *Snapshot rename*: refused 409 `snapshot-held` when the snapshot carries a replication hold (replication finds its common snapshot by name, and ZFS renames a held snapshot); holds that cannot be read, or whose answer does not parse, refuse (`snapshot-holds-unreadable`); checked again in the job. *Snapshot destroy*: a held snapshot is refused 409 naming each hold, with the replication sentence when one is a replication tag; when the holds read fails the request goes to ZFS, which refuses a held snapshot itself. Holders are named by `describeHolds`: the task, `a replication sent here from another cluster node (its task is on that node)` for a peer's tag on a target, `a replication no task names`, the legacy tag, or the foreign tag.

**Target drift** (repl.drift; `services/replication-drift.ts`). ZFS refuses an incremental receive into a target that was written to after the base, and ANAS never passes `-F`. Before a run sends, and on every status read, the target is judged against the snapshot the next incremental starts from with one command: `zfs get -Hp -o property,value,source written@<base>,readonly -- <target>` (over the placement's ssh for a peer or remote). Node ground truth (OpenZFS 2.4.2): a read-only replica is not changed by reads, browsing `.zfs`, snapshots of it or a `readonly` toggle; with `readonly=off` and access-time updates on, reading one file changes it. Four states:

| State | Read | A run with something to send | A run that is up to date |
|-------|------|------------------------------|--------------------------|
| `clean` | `written@<base>` = 0, `readonly` on | sends | settles holds, nothing said |
| `exposed` | 0, `readonly` off | sends; warning that the receive set it read-only again | warning; recorded in the result |
| `modified` | > 0 | refused before any snapshot, hold or send; the job fails and records it | completes with the warning; notified at error severity (`completed, target changed`) |
| `unknown` | the read failed, timed out or did not parse | sends, with a note that ZFS refuses it if the target was changed | note only |

A read that fails never reads as clean. The `modified` sentence names the dataset and the remote, the bytes written, the target's snapshots newer than the base, the way back (`zfs rollback -r <target>@<base>` on the target, which discards what was written since), and whether the base is still held on each side (read with `zfs holds`; another tag on it is said, since ZFS keeps any held snapshot; an answer that does not parse is "could not be read"). A refused run moves no hold, takes no snapshot (every refusal runs before the snapshot-first snapshot) and leaves the task enabled; an up-to-date run says which holds its settle placed and released. A recursive task is judged per copy by the run's own planner in the run, the status read and the daily check; when the tree cannot be read or planned its state is `unknown` with what could not be read, unless the root itself reads `modified`. A recursive run with a changed copy fails the job, including a copy that is up to date; a single up-to-date run completes. *Notifications* come from runs and the daily check only, never from a read: `modified` at error severity, `exposed` at warning, `unknown` and `clean` none. *The dashboard* opens no ssh: a remote target's state is the one its last run recorded in the journal, shown with that run's time. *The daily check* (`anas-replcheck.service` and `anas-replcheck.timer`, `OnCalendar=daily`, `Persistent=true`, runner `dist/repl-drift-check.js`; the daemon writes the pair with the first replication task and removes it with the last, serialised in-process) reads every enabled task that has not run for 24 hours and is not running, and notifies only for `modified` (`daily check: target changed`, error severity), after reading the target's snapshot listing again: a listing that changed between the two reads is a receive in flight, and that verdict is dropped with a journal line. *Cost*: one command per single run (two more holds reads when modified); a status read of a local single task three `zfs` commands, of a recursive task eight plus one per copy with a target-only snapshot after its base; a remote task's row in the Replication view about three ssh commands per refresh (six for a recursive task), none from the dashboard.

**Recurring tasks** (`routes/replication-tasks.ts`, `services/replication-units.ts`). The store is the systemd units: `anas-repl-<name>.service` and `anas-repl-<name>.timer` in `/etc/systemd/system`, per node. The service carries the task as JSON on a `# X-ANAS-Task=` line, the only thing read back, plus `Type=oneshot` and `ExecStart=/usr/bin/node /opt/anas/packages/daemon/dist/replicate-task.js <flags>`; the timer carries `OnCalendar=<schedule>`, `Persistent=true` and `WantedBy=timers.target`. The schedule is checked with `systemd-analyze calendar` before anything is written (`Invalid schedule '<schedule>': <error>`). `ReplicationTask = {name, source: {pool, dataset}, target, schedule, snapshotFirst (default true), enabled (default true), notify (default on-failure), recursive?, exclude?}`. A stored task that fails the strict schema but parses leniently is listed with `invalid: true` and `invalidReason` so it can be repaired or removed. Create refuses an existing name (`409`), a source pool missing on this node, and every target-guard sentence above. An update is bound to the sha256 of the stored service unit (a unit changed meanwhile answers `409 STATE_CHANGED`) and refuses a body whose `name` differs from the URL. Delete removes both units, the timer's `Persistent` stamp and the failed state, and touches nothing in ZFS. Run now submits a job that runs `systemctl start --no-block anas-repl-<name>.service`, so a manual and a scheduled run go through the same unit and share one history; delete and run are refused while a run is active, and a run state that cannot be read refuses.

The flags the timer passes (`runnerArgs`), in this order: `--pool <pool> --dataset <pool-relative dataset, '' for the pool root> --target-pool <pool>`, then `--target-dataset <path>` when it is not empty, `--location-kind <peer|remote> --location-name <name>` for a non-local target, `--snapshot-first` when on, `--notify always` only for `always`, and last `--recursive` followed by one `--exclude <dataset>` per entry. The runner refuses `--exclude` without `--recursive` and `--recursive` with `--snapshot-first` (exit 2), POSTs the dataset's `…/replicate` route over the daemon's Unix socket with the task runner's identity (uid 0, `Sys.Audit,Sys.Modify`; `identityHeaders` in `runner-poll.ts`), polls the job to its end, prints `{task, result}` as JSON on stdout (journald), and exits 0 when the job completed, 1 when it failed, 2 on an argument or transport error (`replicate-task.ts`). The runner's body for a recursive task carries `recursive: true`, `snapshotFirst: false` and the exclude list.

A **retarget** needs `?retarget=true`: a PUT that changes the source, the target (pool, path or location) or `recursive` is otherwise refused with `This edit would move replication task '<name>' (<changes>). Retargeting changes where data is read from and written to — resend with ?retarget=true to confirm it is intended.`, the changes reading `source <was> → <now>`, `target <was> → <now>`, `recursive on → off` (`endpoints`). Schedule, `snapshotFirst`, `notify`, `enabled` and the exclude list change freely.

**Status** is derived on every read, from ZFS and systemd (`deriveTaskStatus`): `lastReplicatedSnapshot` is the newest source snapshot (transients aside) that the target also has, `lastReplicatedAt` its creation time, `snapshotsBehind` the number of source snapshots newer than it (all of them when the target has none); a peer or remote target is read over ssh (`readRemoteSnapshotNames`). The three fields are `null` when the source listing or the target listing could not be read (a location that does not resolve, an ssh or ZFS failure, a local listing that failed); a target ZFS says does not exist counts every source snapshot as behind. A `systemctl show` that could not answer marks the row `statusUnreadable: true`. `lastRunResult` (`success`, `failure`, `running`, `unknown`, `disabled`, `never-run`), `nextRunAt` and `lastRunNote` come from the units, the runner's journal line and the timer (`deriveUnitRunStatus`). A task whose last run failed raises a dashboard warning of category `replication`.

**Notifications** (`services/replication-notify.ts`). `notify: always | on-failure`, default `on-failure`. The replicate job is the one place every run passes through, the timer's and the panel's alike, so it emits the notification, with the mode the request carried (the runner forwards the task's). A success notifies only under `always`; a run that completed with warnings and a failure notify under both. Delivery is `PVE::Notify` with the template and `type` `anas-replication`, severity `info`, `warning` or `error`; the subject is `replication <source> -> <target>[ (<kind> '<name>')] succeeded | completed with warnings | FAILED`, and the body lists source, target, location, result, duration, snapshot, mode with its base, the warnings and the error verbatim. A delivery failure never fails the run.

**Recursive replication** (`recursive: true`; `runRecursiveReplication`). One snapshot name S is sent across a swept tree, one `zfs send | zfs recv` per dataset, with the argv of the single-dataset table, in listing order. `zfs send -R` is never used, and neither are `-p`, `-F`, `-w` or `-I`. The reason is what a replication stream does on the receiving side; `zfs-receive(8)`: "When a snapshot replication package stream that is generated by using the zfs send -R command is received, any snapshots that do not exist on the sending location are destroyed by using the zfs destroy -d command."; and `zfs-send(8)` on `-R`: "When received, all properties, snapshots, descendent file systems, and clones are preserved." and "If the -R flag is used to send encrypted datasets, then -w must also be specified." With one plain send per dataset the target keeps the snapshots the source no longer has, the stream carries no dataset properties (`-p`, "Include the dataset's properties in the stream. This flag is implicit when -R is specified.", is not passed), and an encrypted child is sent without `-w`.

*Sweep and excludes.* The sweep is the recursive snapshot schedule's: `zfs list -H -o name -r -t filesystem,volume -- <root>`, the root first and then its descendants in listing order (a parent before its children), minus each excluded dataset with everything beneath it (`sweepSet` in `services/zfs-snapshot.ts`). Each dataset's target is the target root plus the dataset's name below the source root (`treeTargetName`): `tank/data/a` with the target root `backup/data` lands at `backup/data/a`. Zvols are swept and sent like filesystems. An exclude entry is a full dataset name; it must be a child of the source (`Exclude '<name>' is not a child dataset of '<root>'`) and needs `recursive` (`Exclude requires a recursive replication`) — the schedule's own rule, `excludeShapeIssue`. Whether it exists is asked at task create and update. At a run, an entry that names no dataset is inert: it is reported in the result as `excludeMissing` (a note, no warning), and it does not excuse a local target placed under it.

*Reads.* Every fact is read before the first send, each with one command judged by its exit code (`readTreeFacts`); a read that fails, an ssh that cannot connect, or a line the parser cannot read refuses the run, and none is ever taken to mean "absent", "no snapshots", "not encrypted" or "not modified" (ground truth `fixtures/zfs/replication-tree/README.md`: a missing dataset and an empty one differ only by the exit code). The reads, in order: the source tree (it must start with the root's own row); the source tree's snapshots, `zfs list -Hp -t snapshot -o name,creation,guid -s createtxg -r -- <root>`, ordered newest first by `createtxg`, the order ZFS took them in; the source tree's `keystatus`, `zfs get -Hp -r -t filesystem,volume -o name,property,value keystatus -- <root>`; the target POOL's tree, whose first row must be the pool, and from which the target root's existence is read; and, when the target root exists, its snapshots and its `written` property. The parsers (`parsers/zfs-tree.ts`) refuse a carriage return, a wrong number of fields, a repeated row and an empty creation time (`Unreadable <listing> line: '<line>' — refusing the recursive replication`). The read refusals: `Could not list descendants of '<root>' — refusing the recursive replication`, `Could not list the snapshots under '<root>'[ on the target] — refusing the recursive replication`, `Could not read the encryption state under '<root>' — refusing the recursive replication`, `Could not list the datasets of pool '<pool>' on the target — refusing the recursive replication`, `Could not read the modification state under '<target root>' on the target — refusing the recursive replication`.

*S and the per-dataset plan* (`planTreeReplication`). S is the root's newest snapshot that is not a backup or cloud transient. For each swept dataset: a dataset without `@S` whose target name has no dataset on the target is **skipped** with everything beneath it, and the run completes with the warning `'<dataset>' has no '@<S>' (created after that snapshot?) — skipped with everything below it; it is sent once a recursive snapshot of '<root>' includes it`; a dataset without `@S` that has a copy refuses the run; a dataset with no copy is sent in full; any other copy is judged by the single-dataset base rule (`decideBase`, step 5 above): a copy that already has `@S` is listed `upToDate` and nothing is sent for it (`holdsKept` lists those whose holds stay because the copy's newest snapshot is a transient newer than S that the source still has), a copy with a base is sent incrementally from it, and every other copy refuses the run with that rule's sentence.

*Preconditions.* All of these are settled before the first send. The exclude shape and the ownership check refuse first; the planner then collects every refusal it finds in one pass; the snapshot names are checked after the plan and the local target guard last. Refusals of one stage are joined with `; ` into one sentence.

| Precondition | Refusal (exact text) |
|--------------|----------------------|
| The root has a snapshot | `Dataset '<root>' has no snapshots — take a recursive snapshot of it, or let its recursive schedule run` |
| No swept dataset, the root included, is PVE-owned (`ownershipOf`, `ownedDescendant`) | `Recursive replication of '<root>' would include <dataset> — <reason> — exclude it, or replicate a dataset below it` (`409 PVE_MANAGED`) |
| Every target name is at most 255 characters and passes `DatasetPath` (`treeTargetNameRefusals`) | `'<dataset>' cannot be replicated: its target name '<target>' is longer than ZFS allows (255) or contains characters ANAS does not pass to a remote command` |
| A local target root is not inside the source tree, unless it sits under a live exclude | `The target '<target root>' is inside the source tree '<root>' — a recursive replication would copy its own replica; choose a target outside it, or exclude the dataset that contains it` |
| A local source root is not inside the target tree | `The source '<root>' is inside the target tree '<target root>'` |
| Every swept dataset is unencrypted or has its key loaded (a non-raw send of a dataset whose key is not loaded sends nothing — fixture README) | `'<dataset>' is encrypted and its key is not loaded — load it or exclude the dataset`; a missing row: `Could not read 'keystatus' of '<dataset>' — refusing the recursive replication` |
| A dataset without `@S` has no copy on the target | `'<dataset>' has no '@<S>', the newest snapshot of '<root>' — recursive replication sends one snapshot name across the tree; take a recursive snapshot of '<root>' (or let its recursive schedule run), or exclude '<dataset>'` |
| A new copy's parent exists on the target or is created earlier in the same run | `'<target>' cannot be created: its parent does not exist on the target and is not part of this run` |
| No copy has been changed since the snapshot its next send starts from (target drift, below: `written@<base>` = 0; a non-zero value is what makes a receive fail with "cannot receive incremental stream: destination <dataset> has been modified since most recent snapshot" — fixture README). The request answers 202 and the job fails before the first send, recording every changed copy | the `modified` sentence of target drift, one per changed copy; a tree read that fails refuses as before (`Could not read 'written' of '<target>' — refusing the recursive replication`) |
| Every copy that is not up to date has a base by the single-dataset rule (`decideBase`) | nothing in common: `Target '<target>' has diverged — no common snapshot; remove the target dataset or replicate to a new path`; a copy already past S, or common snapshots none of which is a base: the rule's sentence from step 5, the latter naming the common snapshots and `zfs rollback -r` |
| S and every base pass the shared `SnapshotName` (letters, digits, `_ - . :`) | `Snapshot '<name>' has a name ANAS does not pass to a remote command (a space or another character outside letters, digits and _ - . :) — rename it with 'zfs rename', or take a new recursive snapshot of '<root>'` |
| A local target: every target name the run writes or holds (planned and up to date) passes the target guard | the guard's sentences above |

Two more refusals come from the request itself: a named snapshot (`Recursive replication sends the newest snapshot of the source across the tree — it cannot be combined with a named snapshot`), and snapshot-first, which the schema refuses (`Recursive replication sends the snapshots a recursive snapshot schedule takes — turn off 'Take a fresh snapshot before each run' and schedule the source recursively in the Snapshots menu`). Snapshot-first is unavailable with recursion because it would take a fresh `snapshot-<time>` on every run, a name no retention prunes; a recursive task sends the snapshots a recursive snapshot schedule already took (`RECURSIVE_SNAPSHOT_FIRST_REFUSAL` in `schemas/replication.ts`).

*The run.* The root pair passes the single-dataset target guard at the request; the reads and every gate above run at the request (`400`, or `409 PVE_MANAGED` for ownership) and again in the job on a fresh PVE footprint, where any refusal fails the job as `409 STATE_CHANGED` before anything is sent. The job holds a shared claim on every swept dataset and, for a local target, an exclusive claim on the target root, in the `long` lane. It first settles the holds of the up-to-date copies, then sends the planned datasets in sweep order, each followed by its hold settle. The first failed send ends the run: `Replication failed at '<dataset>' — <detail>; already sent this run: <datasets, or nothing>; the next run continues from each dataset's own base`, the detail carrying the single-dataset run's modified-target hint (step 7) when ZFS gives that refusal. Nothing is rolled back. A failed receive leaves no snapshot and no resume token on the target (fixture README), so the next run finds the finished datasets up to date and sends the rest from their own bases.

*Holds per dataset.* Every dataset in the run is held under ONE tag, the one derived from the target root (`replicationHoldTag(location, <target root>)`), with the same settle as a single dataset, so a refused destroy of any child names the task that owns the tree. A hold failure is a warning prefixed with the dataset's name; the legacy migration is considered for the root only.

*Nothing on the target is destroyed.* No receive carries `-F` and no `zfs destroy` runs against the target. Datasets under the target root that the sweep does not cover are listed in the result as `targetOnly`; a copy of a dataset excluded later is kept and no longer updated.

*Result and notification.* `{recursive: true, mode?, snapshot, target, holdTag, datasets: [{dataset, target, mode, baseSnapshot?, bytesEstimated}], upToDate, holdsKept?, skipped, targetOnly, excludeMissing?, bytesEstimated, warnings?}`; `mode` is `full` when any dataset was sent in full, `incremental` otherwise, and absent when nothing was sent. The notification adds `Datasets: <n> sent, <m> up to date` and one `<dataset> -> <target> (<mode>)` line per sent dataset. At the request, a missing source, the root pair's target-guard refusal, the named-snapshot refusal and every refusal from the reads and the gates are notified as a failed run under the request's mode, as a refusal in the job is; only a body the schema refuses is answered without a notification. The single-dataset run does the same: its refusals at the request (a named transient, a missing source, a PVE-owned snapshot-first source, the target guard) are notified as a failed run under the request's mode; a body the schema refuses is not.

*Task fields and the PUT contract.* A task carries `recursive?: boolean` and `exclude?: DatasetPath[]`; absent stays absent, and a task without `recursive` runs the single-dataset path with its argv unchanged. Because `snapshotFirst` defaults to `true`, a recursive create must send `snapshotFirst: false`. Create and update of a recursive task also check, in order (first refusal answers, `400` or `409 PVE_MANAGED`): the source dataset exists (`Source dataset '<source>' does not exist`; an unreadable listing: `Could not list descendants of '<source>' — refusing the recursive replication task`); every exclude exists unless the stored task already carried it (`Exclude '<name>' does not exist under '<source>'`); no swept dataset is PVE-owned; the target names and the placement; and, for a local target, the target guard for every swept dataset. Snapshots, keys, `written` and divergence are left to the run, so a task can be saved before its source has a recursive snapshot. A PUT that omits `recursive` keeps the stored value; one that omits `exclude` keeps the stored list while the task stays recursive; a key that is present stands, `false` and `[]` included; the merged task is judged by the strict schema before it is written. A client that omits `recursive` on a stored recursive task and sends or defaults `snapshotFirst: true` therefore gets the snapshot-first refusal instead of a converted task. Lag and status stay derived from the root.

*The panel* (`65-replication.js`, with the shared `ANAS.excludePicker` in `10-api.js`). The task dialog has **Recursive — Include child datasets** and, while it is ticked, **Exclude datasets**: a tag picker over the strict descendants of the source picked, read from the pool's dataset listing, with PVE-owned datasets listed under their badge so they can be excluded; a stored entry the listing no longer returns stays selected and is marked "(unavailable)". Its hint reads "Each excluded dataset is skipped together with everything beneath it. Datasets PVE owns are listed so they can be excluded. A copy of an excluded dataset already on the target is kept and no longer updated." Ticking Recursive turns "Take a fresh snapshot before each run" off and disables it, with the hint "Off while child datasets are included: a recursive task sends the snapshots a recursive snapshot schedule of the source already took. Schedule the source recursively in the Snapshots menu."; un-ticking restores its earlier value. A ticked dialog sends `recursive: true`, the exclude list (`[]` when empty) and `snapshotFirst: false`; un-ticking a stored recursive task sends `recursive: false, exclude: []`, and the retarget confirmation says "Child datasets: only the source dataset is replicated from now on; the copies of its child datasets already on the target are kept and no longer updated." A recursion-only change is confirmed under the title "Change what the task replicates", and any confirmation lists the stored excludes the edit stops sending ("No longer excluded: <names>"). The Enable/Disable toggle sends the recursion fields back unchanged. The grid marks a recursive task `(-r)` or `(-r, <n> excluded)` beside its source, with the excluded names in the tooltip. After a save with Recursive ticked, the panel reads the task list back from the same node: when the stored task lacks `recursive`, it shows "This node's ANAS does not support recursive replication. The task "<name>" was saved as a single-dataset task: it replicates <source> only, with "Take a fresh snapshot before each run" off. Edit it, or update ANAS on this node."; when the task is missing from the list or the read fails, it says the recursion could not be confirmed. On a cluster where nodes run different ANAS versions, a node whose daemon predates the fields drops `recursive` and `exclude` from the body and stores a single-dataset task; the read-back is where the operator learns that. **Run now** waits for the job that starts the task's unit (`systemctl start --no-block`) and then says "Replication started: <name>"; the run's outcome is read from the Last run column and from the notification. The one-off Replicate dialog and the plan route have no recursive option.

**Known limits.**

- PVE ownership of a peer or remote target is not checked: the target guard reads only this node's `storage.cfg` (`guardReplicationTarget`).
- A peer or remote target root carries no claim, so two runs into it from different tasks or requests are not serialised (`runReplication`, `runRecursiveReplication`: the target claim is taken for a local target only).
- Holds on a dataset that is excluded later, or on the children of a task whose recursion is turned off, stay until they are released by hand with `zfs release <tag> <snapshot>`; a run settles holds only on the datasets it plans or finds up to date.
- When the root's newest snapshot was taken of the root alone, a recursive run refuses while any child has a copy on the target, until the next recursive snapshot of the root.
- A dataset whose name contains a space fails `DatasetPath`, so it can be neither a source nor an exclude entry; a tree that contains one is refused by the target-name check unless an excluded ancestor covers it.
