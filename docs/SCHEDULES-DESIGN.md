# Schedules — uniform ANAS-owned snapshot scheduling (+ scrub surfacing)

**Status:** designed 2026-07-26. **Supersedes the 17.1 `sanoid` tool pick.** That decision was made for ZFS before the operator required schedules **uniform across AHR and ZFS**; `sanoid` is ZFS-only, so it cannot deliver uniformity. We keep the *learning* from sanoid (its retention model, captured in docs/SCHEDULES-GROUND-TRUTH.md) and manage the schedule ourselves.

## Guiding principle (operator, 2026-07-26)
**ZFS and AHR function EXACTLY THE SAME with respect to snapshots, scrubbing, and pruning — one uniform user experience — even though the underlying mechanisms differ.** The operator schedules/toggles/prunes a ZFS dataset and an AHR pool through identical controls; ANAS dispatches to the filesystem-appropriate backend behind that uniform surface. (This is [[feedback-parallel-construction]] applied end to end.) Dropping sanoid also removes an external dependency — more guest-faithful (we don't bend the system around a third-party tool's config + timers).

## Decisions
- **No sanoid.** Nothing sanoid does that we'd use is irreplaceable: its keep-N-per-period retention is a simple algorithm (we replicate it, using sanoid's proven bucketing as the reference); its extras (Nagios `--monitor`, `syncoid`) we don't use; its hold-handling is *worse* than detecting+skipping holds; and it's ZFS-only. The 17.2 `sanoid.conf` parser is now dead product code — remove it during the build (the ground-truth learning carries forward, the parser doesn't).
- **Mechanism: systemd timers** (not cron). `Persistent=true` catches runs missed during downtime (a NAS reboots; a snapshot scheduled while off fires on next boot — cron can't); journald observability; matches the replication task-store's systemd-unit pattern (Epic 5.5). ANAS authors one templated timer+service per schedule (surgical, guest philosophy).
- **Scope:** ANAS-managed pools/datasets only. PVE-managed pools stay hands-off / display-only (3.25).

## Uniform snapshot model (AHR btrfs AND ZFS — one policy, one screen, one mechanism)
A **snapshot schedule** = `{ target, cadence, retention, recursive?, exclude? }` where target is a ZFS dataset or an AHR pool. On timer fire ANAS runs the filesystem-appropriate command behind one uniform policy:

| | Take | Prune (over-retention) | Hold-safety |
|---|---|---|---|
| **ZFS** | `zfs snapshot [-r] <ds>@anas-<bucket>-<utc>` | `zfs destroy` the excess | SKIP `userrefs>0` (held, e.g. a replication base); surface as "retained (held)" — never a failed-destroy |
| **AHR** | ro btrfs snapshot `@data → @snapshots/anas-<bucket>-<utc>` (reuse 11.12 primitives) | `btrfs subvolume delete` the excess | n/a (btrfs snapshots aren't ZFS-held; AHR replication is separate) |

- **Exclude (snapx.1, #71).** A recursive ZFS schedule may name child datasets to skip (`exclude`: full paths, each a strict descendant of the target; skipped with its whole subtree). With an exclude list the take lists the tree (`zfs list -H -o name -r -t filesystem,volume`), drops the excluded subtrees and takes the rest in ONE `zfs snapshot a@n b@n …` call, which ZFS performs atomically, so the consistency of `-r` is kept; without one it stays the literal `-r`. The PVE-owned-descendant guard (create, update and every run) runs on the tree minus the excluded subtrees, and its refusal says the owned dataset can be excluded. Exclude on a non-recursive or AHR schedule is a 400.
- **Ownership stamp (ident.1, 2026-10-06; supersedes the name-pattern and witness rules below for ZFS).** Every ZFS schedule take runs `zfs snapshot [-r] -o anas:schedule=<id> …` — one atomic verb, the property on every snapshot of the call. The inventory reads `anas:schedule` with its SOURCE: only `local` stamps count (a `received` stamp is the sender's, never ours, noted `N left: received`). Prune candidates are this schedule's stamped snapshots only; another id, including a deleted schedule's, is never a candidate. An unstamped `anas-<bucket>-*` snapshot (pre-0.4.2 take) is a candidate only when the schedule list is complete and no other enabled schedule covers that dataset, else left with a note — that is how legacy droppings converge without a second schedule's history being touched. A bucket absent from the policy is left alone; the schedule's own cadence bucket is always planned (0 when absent, else an hourly schedule on a daily preset would grow forever). Excluded datasets: this schedule's stamped snapshots are destroyed outright, unstamped ones noted. Fail-safe on an incomplete list now holds back only unstamped snapshots (stamped ones are provably ours). The name+txg+creation witness and the most-generous-count rule are retired. Not done (identity epic): re-reading the schedule inside the fire job. AHR schedules unchanged.
- **Prune per dataset (snapprune.1, 2026-10-05).** A recursive ZFS schedule's prune reads the whole subtree's snapshots in one `zfs list -t snapshot -Hp -o name,creation,userrefs,createtxg -r <target>` and plans PER DATASET, destroying one snapshot at a time after a `userrefs` re-check (never `destroy -r`: one held child would fail the verb). Three scopes: the **target** gets the full policy as before; a **swept** child (one the take covers) is planned on this schedule's bucket only, BY NAME (the schedule took them with `-r`; a replica kept under the target must be excluded), keeping the most generous count among the enabled same-bucket schedules that cover it, so a pool-wide `hourly:24` never cuts a child's own `hourly:168` on the parent's run — the child's own run still applies its own policy (one-directional; a symmetric rule is a later candidate; disabling the child's own schedule removes its cover on the parent's next run, by design, no hint — test-review ruling 2026-10-06); an **excluded** dataset (under the target, outside the sweep) is left to another enabled same-bucket schedule that covers it, else this schedule's provably-own snapshots there (same name, same `createtxg` AND same creation second as an ANAS-sourced snapshot still in the sweep — one `-r` or multi-name take is one txg; residual: a foreign snapshot with the same name in the same txg and second would match) are destroyed outright, PVE-owned or not, while everything else (received snapshots, other buckets) stays with a per-dataset note; a refused destroy on any swept or excluded dataset is noted per dataset and the run ends `warning`; on the target it fails the run as before. Held snapshots never consume a keep slot (GT-7, kept) and are reported only when an as-if-unheld plan would have pruned them (full review + GLM re-review 2026-10-06: the first fix made holds consume slots and shrank depth by one per hold; corrected). **Fail-safe (review, 2026-10-06):** the covering-schedule rule needs the complete schedule list; when the unit directory cannot be listed or any `anas-snap-*.service` fails to read or parse, that run prunes the target only and leaves every swept child and excluded dataset untouched with the note `N left: schedule list unreadable`. The first run after the fix converges children that accumulated under the pre-fix target-only prune. Known gap: an excluded only child whose names the target has already pruned has nothing left to match, so those stay and are reported. The run result carries `datasets[]` (`dataset, scope, pruned, held, note?`) for the progress line, the journal, the notification and the Run toast.
- **Naming convention** (`anas-<bucket>-<utc>`) marks ANAS-scheduled snapshots; pruning touches ONLY those — never replication bases, manual snapshots, or AHR-manual snapshots (mirrors sanoid pruning only its own).
- Three snapshot lifecycles stay independent and coexist: **scheduled** (this feature), **replication** (Epic 5.5), **AHR-manual** (11.12). The dataset/pool view shows the inventory of all three; Schedules owns only the scheduled policy.

## Retention (learned from sanoid, GT §)
Buckets `frequently / hourly / daily / weekly / monthly / yearly`, keep N of each; **always keep the most recent**; assign each snapshot to its bucket by age and keep the N newest per period. Encode sanoid's proven bucketing so we inherit its edge-case correctness rather than reinventing it. UI: a few **presets** ("24h/30d/12m", "minimal", "aggressive") + an **advanced** expander for raw per-bucket counts (operator's common-case-first instinct).

## Scrub — uniform UX, filesystem-native backend
Scrub follows the same principle: the operator enables/disables/schedules a **periodic scrub** on a ZFS pool and an AHR pool through **identical controls**; the backend differs.
- **ZFS backend:** PVE already monthly-scrubs via `/etc/cron.d/zfsutils-linux`, per-pool-gated by the `org.debian:periodic-scrub` property. ANAS surfaces + toggles that property — same mechanism as PVE, no double-schedule.
- **AHR backend (selfheal.4, 2026-09-11):** ONE ANAS-owned node-level timer, `anas-scrub.timer` (unit-store pattern like the snapshot schedules: `X-ANAS-Schedule=` JSON marker `{ kind: 'ahr-scrub', cadence, pools[] }` in the `.service` **and the `.timer`**), running the WHOLE two-phase scrub per enabled pool in sequence — phase 1 md parity check per band, then phase 2 btrfs checksum scrub + file attribution (selfheal.3). Cadence is node-level: `monthly` (1st Sunday 03:00) or `quarterly` (1st Sunday of Jan/Apr/Jul/Oct). Enabling a pool also disables mdadm's `mdcheck_start`/`mdcheck_continue` timers — ANAS owns md checks on the node, never double-scheduled — and disabling the last pool removes the units and turns mdcheck back on — with no ANAS scrub left the node is stock again, and a stock node has those timers enabled (ruling 2026-09-14); the AHR Scrub *verb* (11.x) remains the on-demand path, and the mdcheck node-global caveat is still surfaced in the state `note` when an outside actor re-arms mdcheck.
- **No adoption, ever (second-pass ruling, 2026-09-13):** mdcheck's timers are enabled by default on a stock node, so "mdcheck is on" is NOT evidence anyone opted into ANAS periodic scrub — the daemon never arms the `anas-scrub` timer (or switches mdcheck off) on its own. A node with no ANAS units and mdcheck enabled is the **legacy state**, reported read-only as `{ enabled: false, mechanism: 'mdcheck-timer' }` with a note: "the OS's monthly md parity check (mdcheck) is on — the distro default, and what ANAS puts back when the last pool's periodic scrub is turned off; enabling ANAS periodic scrub takes it over (md parity + btrfs checksums, two phases)". The per-pool toggle is the ONLY thing that writes units and takes mdcheck over.
- **Uninstall (second pass):** all four ANAS unit families (`anas-snap-*`, `anas-backup-*`, `anas-repl-*`, `anas-scrub.*`) are disabled + removed — their runners are gone with `/opt/anas`, and a timer firing a missing runner is worse than a lost schedule. mdcheck IS re-enabled when a scrub timer was removed (ruling 2026-09-14, reversing the second-pass call): those timers are the distro default, so putting them back restores stock rather than guessing at the node's history, and a node left with no parity check at all is not helping or guarding. The uninstaller says it restored them and prints the `systemctl disable --now mdcheck_start.timer mdcheck_continue.timer` command for an operator who does not want them.
- **Uniform surface:** the Scrubs screen shows "periodic scrub: on/off" identically for both, with the mechanism named where it differs (ZFS: PVE's monthly cron, per-pool; AHR: the ANAS timer — phase 1 parity (md) → phase 2 checksums (btrfs) — with the next run and the node-level cadence).

## Store + Schedules screens (17.3)
- **Schedule store:** the replication task-store pattern — the systemd timer/service unit is the source of truth (+ a small ANAS-owned descriptor); node-local (schedules for node-local datasets).
- **Two screens (split 2026-07-27, operator refinement).** The first cut was one "Schedules" screen with a snapshot grid + a scrub grid. On review the operator split it into **two menu entries** — **Snapshots** (`69-snapshots.js`, `ANAS.views['snapshots']`) and **Scrubs** (`69-scrubs.js`, `ANAS.views['scrubs']`) — sitting between Replication and Backup. The bits both screens share (the fs-tag chip so a ZFS and an AHR row read identically, the state pills, and the visibility-gated poll loop) live once in `69-schedules-common.js` (`ANAS.sched.*`) — single-source-of-truth, no diverging copy.
  - **Snapshots:** the uniform snapshot-schedule grid (both fs types) + create/edit/disable/delete with the retention policy; held snapshots shown as intentionally-retained; a **View log** action opens the last-run detail (below).
  - **Scrubs:** the periodic-scrub grid (surfaced from the native mechanisms) + the on/off toggle (+ the node-level monthly/quarterly cadence for AHR); the AHR row states both phases and the next run, and the mdcheck **node-global** caveat is surfaced per-row and confirmed on toggle.
  - overdue/failed schedules on the dashboard (17.7, matching the replication policy).
- **Last-run log + exit status (snapshots).** `GET /v1/schedules/:id` returns a **detail** — the status fields plus `lastRunExitCode` (systemd `ExecMainStatus`), the `.service`/`.timer` verbatim, and a bounded recent `journal` blob (`journalctl -u anas-snap-<id>.service -n 200 -o short-iso --no-pager`). This **mirrors the backup task detail** (`GET /v1/backup/tasks/:name` → `journal` via `readRecentJournal`): the same last-run logs + exit-status surface, the same shared-schema shape (`SnapshotScheduleDetail` ↔ `BackupTaskDetail`), the same UI rendering (exit status labeled, the journald `<pre>` with the "older history is not retained" caveat). The service-unit journal is populated by the timer's own fire (the runner prints its result JSON to journald and exits 0/nonzero), so a scheduled run's log and exit code are truthfully captured; a manual Run-Now takes+prunes in the daemon (no unit-journal entry) — the log window is about the scheduled/service history.
