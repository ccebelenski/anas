# REAL CAPTURE from the disposable stunt node anas-pve (cr3.nodefix review R2, 2026-11-15).
# kernel 7.0.14-28-pve, btrfs-progs 6.14. An AHR pool made through the API (POST /v1/ahr,
# 2 disks, ahr1) and mounted the way ANAS mounts every AHR pool: subvol=/@data at
# /mnt/anas-ahr/nfxahr. Root makes a subvolume `sv` and plain folders; `udir` and
# `share` are given to nobody, and nobody (setpriv, no capabilities) makes two
# subvolumes whose names hold a line break: `udir/nl<LF>name`, and
# `share/victimdir<LF>ID 9999 gen 1 top level 256 path accounts` beside root's
# plain folder `share/victimdir`.
# Two sittings on the same pool, nothing in between: the first block, then the
# `--format json` and `find` commands again with stderr in line (in the first
# sitting their stderr arrived out of order and is not repeated here).
# Nothing was edited: these are the exact bytes the commands produced.
#
# WHAT IT SHOWS: (1) a user without privileges can create a subvolume; (2) plain
# `btrfs subvolume list` prints the name RAW, the line break included (od -c), so
# a name can carry a whole well-formed list line; (3) this btrfs-progs has no
# structured form of the list (`--format json` is unsupported for `subvolume list`
# and `subvolume show`); (4) every subvolume root is inode 256 on a device number
# of its own (92, 93, 94), the mount's own root is inode 256 on 91, and an
# ordinary folder is another inode on the mount's device 91; (5) `find <mount>
# -inum 256 -name '*[[:cntrl:]]*'` lists the subvolumes whose names hold a
# control character.
# ==============================================================================
