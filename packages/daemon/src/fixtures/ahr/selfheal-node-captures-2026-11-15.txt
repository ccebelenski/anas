## ROW 2

**Verdict ROW 2.** After a hole is punched over the bad block the scrub **DOES
NOT name the file again** — there is no `(path: f1.bin)` line — **but it DOES
still report a checksum error at the same logical/physical**: `csum=1`,
`Uncorrectable: 1`, logged as `scrub: unable to fixup (regular) error at
logical 14860288 ... physical 14860288`. The restore control (writing the original
bytes back to the member) makes the same scrub report `no errors found`, so the
post-punch `csum=1` is exactly that physical block, not a stale counter.
Mechanism seen here: `fallocate -p` removed the file's logical mapping for block
300 (filefrag shows the hole) but the 4 MiB physical extent stayed allocated
(extent tree unchanged) and the csum still covers the logical, so the scrub keeps
reading and failing it — it just has no file (no extent backref at that offset)
to name.

## ROW 4

**Verdict ROW 4.** After the rebuild the array's parity **DOES agree with the
rotten block**, and the scrub **DOES still name the file**. Plainly: failing the
parity member and rebuilding the spare recomputed that parity from the rotten
data, so `mismatch_cnt` fell **8 → 0** and the rebuilt parity row equals
`XOR(slot0, slot2_rot)` — md-level consistency is restored over corrupt data. The
data itself was never touched, so a `btrfs scrub` still reports
`checksum error ... (path: f1.bin)` and `csum=1`. A rebuild (and a clean `md check`)
therefore blesses the rot; only the filesystem checksum still names the file.
